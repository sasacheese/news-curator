# news-curator

関心のあるトピックの最新情報を、**毎朝 8:00 までに「前日 7:00 からの 24 時間」分だけ集めて、30 分でキャッチアップできる形に要約する**ツールです。

- 収集・要約は GitHub Actions が毎朝 7:00 JST に起動し、8:00 までに読める状態になります（PC を起動していなくても動きます）
- 結果は GitHub Pages の静的サイトで読みます（スマホからも見られます）
- 概要・リンク・キーワードは Git 管理の JSON に貯まるので、「あれ何だっけ」をあとから全文検索できます

サーバー費用は **0 円**（public リポジトリの GitHub Actions + Pages は無料枠）。かかるのは Claude API の実費だけで、**1 日およそ 20〜30 円 / 月 700〜900 円**が目安です。

---

## セットアップ

### 1. リポジトリを push する

```bash
git push -u origin main
```

### 2. Claude API キーを Secrets に登録する

[Anthropic Console](https://console.anthropic.com/settings/keys) で API キーを発行し、
リポジトリの **Settings → Secrets and variables → Actions → New repository secret** で登録します。

| Name | Value |
| --- | --- |
| `ANTHROPIC_API_KEY` | `sk-ant-...` |

> キーを登録しなくてもツールは動きますが、スコアリングがキーワードマッチだけになり、
> 「何ができるようになるか」「試し方」の解説は生成されません。

任意で、Qiita API のレート制限（未認証は 60 リクエスト/時）を緩めたい場合は `QIITA_TOKEN` も登録できます。

#### connpass の API キー（コミュニティ情報を使う場合）

日本語のイベント・もくもく会の母集団は connpass が圧倒的に大きいので、
コミュニティ情報を使うならここが本命です。**API キーが必須**で、
個人・コミュニティ利用は申請すれば無償です（発行まで 1 週間目安・追加発行なし）。

1. [利用申請フォーム](https://forms.gle/FD6h9sKGCLXBPohZ8)から申し込む
   （利用目的が審査対象なので、用途・取得頻度・リポジトリ URL を書く）
2. 届いたキーを `CONNPASS_API_KEY` として Secrets に登録する

未登録でも動きます。その場合は Doorkeeper と confs.tech だけで集め、
コミュニティタブの冒頭にその旨が出ます（もくもく会はほとんど拾えません）。

Doorkeeper は未認証でも `events` が読めますが、公式ドキュメントでは
Public API Access Token が必要とされています。閉じられたら
プロフィール画面で発行して `DOORKEEPER_TOKEN` に入れてください。

### 3. GitHub Pages を有効にする

**Settings → Pages → Build and deployment → Source** を **GitHub Actions** にします。

### 4. 最初のダイジェストを生成する

**Actions → Daily digest → Run workflow** を実行します。2〜3 分で
`https://<あなたのユーザー名>.github.io/news-curator/` にダイジェストが出ます。

以降は毎朝自動で更新されます（起動は 7:00 JST、読めるようになるのは 8:00 まで）。

## 何をどこから集めているか

前日 7:00 〜 当日 7:00（JST）に公開されたものだけが対象です（コミュニティ情報だけは
別の軸で引きます。後述）。設定は 3 つに分かれています。

- `config/watchlist.json` — **どこを監視するか**（リポジトリ・フィード・CHANGELOG）。運用中に増減する部分
- `config/sources.json` — 各ソースの有効/無効と取得量のチューニング
- `config/community.json` — イベント情報の**行ける範囲**と検索語

| ソース | 内容 |
| --- | --- |
| Qiita | 全新着記事（LGTM・ストック数つき） |
| Zenn | daily トレンド + 新着 |
| はてなブックマーク | テクノロジーカテゴリのホットエントリー |
| Hacker News | 一定スコア以上のストーリー |
| dev.to | リアクション数の多い記事 |
| GitHub Releases | ウォッチ対象 35 リポジトリのリリースノート（React / Next.js / TypeScript / Vite / Prisma / Zod / TanStack / Playwright / Claude Code / Codex など） |
| GitHub 急上昇リポジトリ | 直近 3 週間に作られてスターを集めているリポジトリ |
| 公式ブログ RSS | Chrome Developers / web.dev / V8 / MDN / Node.js / TypeScript / React / Next.js / Vite / Vercel / GitHub / Cloudflare / Google Cloud / OpenAI など 22 フィード |
| CHANGELOG | Claude Code の CHANGELOG.md |
| connpass | 勉強会・もくもく会・登壇募集（**API キーが必要**。後述） |
| Doorkeeper | 同上。母集団は connpass より 1 桁小さく、ビジネスセミナーが多い |
| confs.tech | カンファレンスの CFP 締切（`tech-conferences/conference-data`） |

ソースそのものを止めたいときは `config/sources.json` の `enabled: false` を使ってください
（コミュニティ情報は `config/community.json` の `enabled`）。

### 監視対象の追加・削除

`config/watchlist.json` の 3 つの配列を編集するだけです。ダイジェスト画面の「リリース情報」の下に
現在の監視対象一覧と **GitHubで編集** リンクがあるので、そこから Web エディタを開いて
コミットすれば翌朝の実行から反映されます（ローカルに clone しなくても、トークンを用意しなくても構いません）。

```jsonc
{
  // GitHub Releases を見るリポジトリ。owner/repo
  "repos": ["facebook/react", "vitejs/vite"],
  // RSS / Atom。weight は事前スコアの下駄（1〜5、既定 3）で、一次情報ほど高く
  "feeds": [{ "label": "React Blog", "url": "https://react.dev/rss.xml", "weight": 5 }],
  // リリースノートを持たず CHANGELOG.md だけ更新するもの。url は raw、homepage は表示用（省略可）
  "changelogs": [{ "label": "Claude Code", "url": "https://raw.githubusercontent.com/…/CHANGELOG.md" }]
}
```

書式を外した項目は警告を出してスキップし、URL の重複も落とします。1 行の typo でその日の収集が
丸ごと止まることはありません。実行ログの `監視対象: リポジトリ N / フィード N / CHANGELOG N` で
実際に読まれた件数を確認できます。

## リリース情報は別枠

新しい AI モデル・新 API・ライブラリの新バージョン・GA 昇格・新規公開などは、
**ランキングせずに全件**を別セクションに出します。読む価値の順位ではなく
「知っているかどうか」だけで差が出る種類の情報だからです。

### 並べる軸は「何ができるようになるか」

**メジャー / マイナー / パッチという分類では並べていません。** これは仕様上の分類で、
読み手の関心と一致しないからです。実測 27 件で確かめると:

| kind | 件数 | うち「できるようになる」系 |
| --- | ---: | ---: |
| service | 15 | 9 |
| patch | 5 | 2 |
| minor | 4 | **3** |
| ai-model | 3 | 3 |

`service` 15 件の中に「1 サンドボックスで複数エージェントを分離実行」と
「Server-Timing ヘッダーの通過」が同居し、`minor` のほうが打率が高い。
つまり分類の粒度と中身の大きさが対応していません。

そこで `impact`（読者に何が起きるか）を判定させて、それで並べています。

| impact | 見出し | 対象 |
| --- | --- | --- |
| `unlocks` | できるようになったこと | これまでできなかったことが可能になる |
| `security` | ふさがれた脆弱性 | 重大な脆弱性の修正 |
| `improves` | 速く・楽になったこと | 性能・コスト・DX の改善 |
| `chore` | 修正のみ | 新しくできることが増えない（**畳んで表示**） |

各項目には「**〜できるようになる**」の 1 行（`unlock`）を必ず書かせ、
書けなければ `chore` に落とします。分類だけ立派で中身が空、という状態を
構造で潰しています（「安定性が向上する」のような当たり障りのない文も弾きます）。

変化の大きさは形容詞では伝わらないので、読み取れたときだけ差分で見せます。

```
今まで   1 サンドボックスにエージェント 1 つ
これから 1 サンドボックスで複数エージェントを分離実行
```

対応範囲が広がったときは `scope` にバッジが出ます（`iOS` / `Android` /
`セルフホスト` など）。「スマホでも使えるようになった」を一目で分かるようにするためです。

### 脆弱性は別の入口から取る

**リリースノートには脆弱性が載りません。** 実測 27 件でセキュリティの言及は 0 件でした。
GitHub では脆弱性はリリースノートではなく Security Advisory として別に出るため、
監視対象を増やしても拾えません。

そこで [GitHub Security Advisories](https://docs.github.com/en/rest/security-advisories/global-advisories)
を別ソースにしています（認証不要・無料。`GITHUB_TOKEN` があればレート制限が 60/時 → 5,000/時）。

`config/sources.json` の `advisories` で設定します。

```jsonc
{
  "advisories": {
    "enabled": true,
    "severities": ["critical", "high"],
    "ecosystems": ["npm", "actions", "pip", "go"],
    // watchlist.json の repos から名前を導けないものを補う
    "extraPackages": ["@tanstack/react-router"]
  }
}
```

`watchlist.json` の `repos` からパッケージ名を導いて絞り込みます
（`facebook/react` → `react`、スコープ `@facebook/*`）。リポジトリ名とパッケージ名が
ずれるもの（`TanStack/router` の実体は `@tanstack/react-router`）は `extraPackages` に足してください。
**取得件数と採用件数は実行ログに出る**ので、取りこぼしていれば分かります。

LLM は通しません。GitHub が付けた深刻度・CVSS・修正版のほうが、要約より確かで有用です。

実装上の工夫が 3 つあります。

- **モノレポの一括リリースをまとめます。** 実測で `cloudflare/workers-sdk` が
  1 日に 12 パッケージ同時リリースしていました。リポジトリ単位で 1 件にまとめ、
  残りは「同じ製品の他 N 件」の折りたたみに入れます
- **同じ製品の複数告知をまとめます。** Vercel Changelog は 1 日に同じ製品の告知を
  何度も出します（実測で Vercel 4 件・GitHub Copilot 3 件）。同じ種類・同じ製品を
  1 件にまとめ、残りは同じ折りたたみに入れます。実測で 19 件 → 13 件になりました
- **公式ブログのリリース以外を除外します。** Vercel Changelog や GitHub Changelog には
  事業提携・料金改定・導入事例が混ざるので、LLM に判定させて落とします。
  ただし GitHub Releases と CHANGELOG は定義上リリースなので判定を待たずに採用します

リリース情報は深掘りカードにも入りえます（重大なリリースは深掘りする価値があるため）。
その場合は「上で詳説」の印がつき、「その他の注目記事」からは除外されます。

## コミュニティ情報は別のタブ

イベント・登壇募集・もくもく会は、日次ダイジェストには載せずに
**「コミュニティ」タブ**へ出します。記事ともリリースとも軸が違うためです。

**① 時間軸が逆を向きます。** 記事は `publishedAt`（過去）が本体ですが、イベントは
開催日と締切（未来）が本体です。公開ウィンドウで引くと「3 週間前に告知され、
明日が応募締切の CFP」——この枠でいちばん行動価値が高いもの——が**構造的に落ちます**。
ウィンドウを広げる話ではなく、引く軸が違います。だから connpass は開催月（`ym`）で引きます。

**② 毎日同じものが出るのが正しいです。** 記事は再登場させません（掲載済み URL を落とす）が、
イベントは開催まで盤面に居るべきで、消えたら意味がありません。そのため
**重複排除・検索インデックスには通していません。**
代わりに前回の盤面と突き合わせて、無かったものに `NEW` を付けます。
毎日同じ盤面を眺めるので、差分が見えるかどうかがこの画面の読みやすさを決めます。

**③ だから日次に埋めません。** ①②の帰結として、これは「その日の記録」ではなく
**いまの盤面**です。日次ダイジェストに入れると、同じ内容が毎日コミットされ、
過去の日を開いたときに**終わったイベントが並ぶ**ことになります。
保存先は日付を持たない `data/community.json` 1 ファイルで、毎朝まるごと差し替えます。
検索とアーカイブにも入れません（開催が過ぎると価値がゼロになるため）。

### 並べる軸は「今日取れる行動」

「イベント情報」という 1 語に 3 つの別々のニーズが混ざっています。混ぜたまま出すと、
締切が今日の CFP と毎週やっているもくもく会が同じ行に並びます。

| action | 本体になる情報 | 画面での置き場所 |
| --- | --- | --- |
| `speak` | **応募締切**（CFP / LT 枠） | 先頭の「応募の締切」 |
| `attend` | 開催日 + 申込状況（満席か） | 日付ごとのアジェンダ |
| `work` | 直近の開催日だけ | 同上（`もくもく` の印つき） |

**締切を持つものだけ日付の軸から外します。** 開催日で並べると「開催は 3 か月後だが
締切は明日」の CFP が 3 か月先に沈みますが、読者が動くのは締切のほうです。
締切が読めなかったものは開催日側に出るので、同じイベントが 2 度並ぶことはありません。

締切は開催日より先まで見ます（既定 45 日 / 開催は 21 日）。登壇は準備期間が要るので、
締切の 3 週間前に初めて見えるのでは遅く、参加は当日行くだけなので 3 週間先で足ります。
同じ日数にすると、どちらかが必ず合いません。

もくもく会に個別のカードは要りません。読者が知りたいのは「今週末に行ける範囲で
開いているか」だけで、どの会の説明文を読むかではないからです。

### 距離は規模で緩めます

これは知るレーンが「トピック一致を門番にしない」のと同じ形の問題です。近所しか出さないと
TSKaigi / JSConf / ISUCON が構造的に落ち、逆に全国を出すと行けないもくもく会で埋まります。
**規模が距離の免除条件**になります。

| scale | 判定 | 距離の扱い |
| --- | --- | --- |
| `conference` | 名前に `Kaigi` / `Conf` / `ISUCON` / `ハッカソン` など、定員 ≥ 200、複数日開催 | **問わない**（国内かオンラインなら） |
| `meetup` / `recurring` | それ以外 | `location` に一致するものだけ |

カンファレンスでも**海外の現地開催は落とします**。「大きいから知りたい」の範囲を超えるためです。

行ける範囲は `config/community.json` で決めます。

```jsonc
{
  "location": { "prefectures": ["東京都"], "online": true },
  "horizonDays": 21,
  "cfpHorizonDays": 45,
  "keywords": ["React", "TypeScript", "もくもく", "LT"],
  "exclude": ["転職", "案件", "講座", "経営"],
  "cfpTopics": ["javascript", "typescript", "general"],
  "limits": { "speak": 6, "attend": 8, "work": 4 }
}
```

`exclude` はタイトルで落とす語です。**採用イベントや案件紹介は説明文に技術スタックを
並べるので、トピック一致の門番をすり抜けます**（実測で「Javaエンジニア募集！未経験大歓迎！！」が
通りました）。タイトル側で落とすしかありません。

トピック一致の門番は `attend` にだけ掛けています。`speak` は「関心があるか」ではなく
「話せる題材を持っているか」で決まるので一致を要求すると狭まり、もくもく会のタイトルに
React や TypeScript は出てこないので `work` にも要求できません。

同じ主催の会は直近の 1 回に畳みます。連番を振らずに毎週開かれるものも並ぶためです
（実測で Doorkeeper の「Asana Refresh Morning（8月17日）」と「（8月24日）」が別件として出ました）。

ベンダーのウェビナー配信元は**サブドメインを分けて同じ内容を何本も出す**ので、
この畳み込みをすり抜けます（実測で `majisemi-operation` / `-technology` / `-data` が
別主催として 3 件並びました）。タイトルにも共通語が無いため、
`excludeOrganizers` で主催ごと落とします。

### LLM を通すのは「登壇できる」だけ

connpass / Doorkeeper は日時・場所・定員を構造化データで返すので、参加系に要約を通すと
**情報が減ります**（脆弱性を LLM に通さないのと同じ判断）。

`speak` だけは違います。「LT 枠がまだ空いているか」はイベント説明の本文に埋まっていて、
ルールベースだと過去の LT 大会のレポートや「LT を聞くだけの回」まで拾ってしまいます。
ここだけ Haiku を 1 リクエスト通して、募集中かどうか・何を何枠か・締切・
**この読者が出せる題材**を判定させます。

- 募集していないものを「登壇できる」として並べるのがこの枠で一番まずい壊れ方なので、
  迷ったら落とす側に倒しています。**LLM が無い日は `speak` 枠ごと出しません**
  （参加系は残るのでタブ自体は成立します）
- 「出せる題材」は話すレーンの「一次情報を出すとしたら？」と同じ思想で、**名詞句だけを並べて文にしません**。
  文で返ってきたものは発表の代筆なので生成側で落とします（判定は話すレーンと共有）

`speak` が空の日は、connpass のキーが無いか、その日は本当に募集が無いかのどちらかです。
実行ログの `登壇できる: N/M 件が募集中` で区別できます。

## トレンドは別のタブ

**「最新情報」と「トレンド」は別物です。** ダイジェスト本体は前日 7:00 〜 当日 7:00 に
公開されたものだけを扱う差分刊行なので、**昨日の 1 位は今日どこにも出ません**。
これは差分としては正しいのですが、数日続いている話題を追うには向いていません。

実例。`Cursor Origin` は 8/18 の「知る」1 位、`Cursor` の買収は 8/15 の 1 位でした。
どちらも掲載できていたのに、8/19 の画面には出てきません。24 時間ウィンドウと
掲載済み URL の除外が、**まだ続いている話題を構造的に消していた**わけです。

そこで記事ではなく**話題**を単位にして、日をまたいだ状態を別のタブに持ちます。
盤面は `data/trends/board.json` の 1 ファイルで、コミュニティと同じく日付を持ちません
（過去日のアーカイブに埋めると、3 か月後にその日を開いた人へ当時の盤面が出てしまいます）。

**LLM は通しません。全部ルールベースなので追加費用はゼロです。**

### 3 つに割る

| セクション | 中身 | なぜ要るか |
| --- | --- | --- |
| **今日動いた** | 新しく立った話題と、平常より急に本数が増えた話題 | 毎日変わる差分。ここだけ見れば追いつける |
| **追跡中** | 平常より高い水準が続いている話題 | 「ウォッチ」の本体 |
| **落ち着いた** | 数日前まで動いていて、いまは平常に戻った話題 | **終わったことが分かる**と、追う対象を減らせる |

「今日」タブのサマリー直下には、動いている話題のチップだけを並べた帯を出します。
専用タブだけに置くと、毎朝「今日」しか見ない人の目に永久に入りません。
**今日ぶんを見ているときだけ**出します（盤面は日付を持たないため）。

★ を押すと、その話題が帯の先頭に来ます。この端末の `localStorage` だけに持つので、
トークンもサーバーも要りません。

### 判定は「出現の有無」ではなく「水準」で

最初は「直近 7 日のうち 3 日以上出ていれば継続中」で判定していました。
**母集団 572 件を実測したら、これは何も絞れていませんでした**——`Python` `Claude` `Git`
のような語は毎日出るので、出現日数で測ると背景語だけで埋まります。

なので水準（その日の母集団に対する比率）で測ります。

- **平常比** = 当日の比率 ÷ 直近 14 日の比率の平均。生の件数で比べると、ソースを増やした日や
  閑散日がそのまま「急上昇」になります
- **今日動いた** = 当日 3 本以上 かつ 平常比 1.8 以上
- **追跡中** = 直近 5 日の水準が平常の 1.5 倍以上 かつ 直近 3 日にも出ている かつ 直近 5 日で 4 本以上
- **落ち着いた** = 7〜4 日前に 3 本以上 かつ 直近 3 日の水準がその 4 割以下

「落ち着いた」を**直近 3 日が 0 本**で判定していないのが要点です。母集団が大きいと少しは
出続けるので、絶対数では終わりを判定できません。勢いの落ち方で見ます。

**出現日数の多い語は「背景」として名前だけ出します。** 一覧から外すためではなく、
何を外したかを見せるためです。ただし**その日に実際にセクションへ出た話題は背景に載せません**
——同じ語が「今日動いた」と「背景」に並ぶと、読者にはただの矛盾に見えます。

> 追跡中からも背景語を presence で外そうとしましたが、やめました。母集団 572 件では
> `Cursor` のような**追いたい話題も毎日 1〜2 本は出る**ので、出現日数で切ると
> 拾いたいものがまず落ちます。絞りは水準のしきい値だけに任せています。

### 話題名は 2 階層で持つ

固有名詞のまま並べると**表記ゆれで繋がりません**。実データの `Qwen` は
`Qwen` / `Qwen3.6` / `Qwen3.8-27B` / `QwenAudio` に割れていて、そのままではどれも
「累計 1 本」で消えます。かたや抽象カテゴリ（「AI コーディングエージェント」）に丸めると、
それは `topics.json` と同じものになって情報量がゼロになります。

見出しはファミリ、その下に実際に観測された表記を出します。

```
Cursor                          急上昇 ×3.7
Cursor Origin
8/19  allowlist が破れる4パターン        NEW  話す1位
8/18  Cursor Originを触った。第一印象は…      知る1位
8/16  AI coding agentは、なぜ毎回リポジトリを…   話す
```

束ね方には 3 つの規則があります。

- **版名の差は必ず畳む**（`Qwen3.8-27B` → `Qwen`）
- **単語が足されている場合は、子が単独で 5 回以上出ていれば畳まない**。
  `Claude Code` を `Claude` に畳むと別製品の話が 1 つの山になります
- **日別本数が完全に一致する話題は同じものとみなす**。略称は接頭辞では束ねられません
  （`DSH` は `DeepSeek Harness` の接頭辞ではない）。辞書を持つ運用は続かないので、
  データの側から見ます——同じ記事群に当たっていれば日別本数は一致します。
  実測で同じ記事 3 件を持つカードが 2 枚並んだので入れました。残すのは長い名前の側です

### タイムラインは 1 日 1 件

**掲載した記事には印が付きます。** 「8/18 に知る 1 位で出した」と見えることで、この画面が
読み直しではなく**自分が見た地点からの差分確認**になります。トレンド画面が死ぬ一番の理由は
既読の再掲なので、ここが要点です。収集したが載せなかったものには `未掲載` が付きます
——なぜ見た記憶が無いのかが分かるように。

**外国語の記事には日本語の見出しを出します**（掲載側と同じ `titleJa`。原題は hover で読めます）。
日本語の一覧に英語のタイトルだけが混ざると、そこで読むのが止まるためです。

既定で見せるのは**日付の違う 3 件**です。単純に新しい順で 3 件出したところ、今日 3 本ある
話題は 3 行すべてが今日の NEW になり、**どこまで来たのかが完全に見えなくなりました**。
1 日 1 件を代表にして（その日の掲載順位つきを優先）、残りは畳みます。

### 語彙はタグから作らない

話題名の候補は**構造化された・人が付けた名前だけ**にしています。

- 過去 28 日の掲載記事の `keywords`（LLM が名前として選んだ語）
- GitHub の `owner/repo`

タグ（Qiita / Zenn）も試しましたが使っていません。書き手が自分で付けた名前なので
信用できるはずが、**実測の上位が `システム` `tech` `release` `個人開発` `Qiita` で埋まりました**。
タグは分類のための語で、話題の名前ではありません。`owner/repo` もリポジトリ名だけは足しません
（`router` `servers` `container` のような一般語になります）。

タイトルから固有名詞を機械的に切り出す方式は、**部分文字列一致が単語境界を無視して
`RCE` が "source" に、`Pro` が "Provenance" に当たった**ので捨てました。ASCII 語の照合には
単語境界を要求しています。

新しい話題は「一度掲載されたら翌日から語彙に入る」経路で拾います。1 日遅れますが、
名前の質を推測で埋めるよりは確実です。

### 走り始めの数日

平常比も「落ち着いた」も履歴が要ります。台帳が 5 日ぶん貯まるまでは、
**見出しを「今日よく出ている話題」に変えて当日の本数順に並べる**だけにします。
履歴が無い日に全部を「初出」として NEW を付けると嘘になるためです。

台帳（`data/trends/YYYY-MM.json`）は 28 日ぶんを月別シャードで持ちます。
`data/index/` と同じ形なので、過去月は残る日が無くなるまでで書き換わらなくなります。


## 発掘は「2 つの物差しの差」を測ります

「このライブラリ知ってます？あんまり話題じゃないけど便利で」
「これ海外で話題だけど日本ではまだ使われてなくて」——これを**根拠つきで人に言える**
状態にするための枠で、**「発掘」タブ**に出ます。

日次ダイジェストの「作る」レーンとは目的が違います。あちらが出すのは
*今日試したくなるもの*ですが、ここで足りないのは面白い道具そのものではなく
**まだ広まっていないことの証明**です。それが無いと人には言えません
（言った先で「それもう使ってますよ」が返ってきます）。

### 単位は記事ではなく道具

証明は 1 本の記事からは作れません。作れるのは**2 つの物差しの差**としてだけです。

| | 測るもの | 出どころ |
| --- | --- | --- |
| 海外の熱 | npm の週間ダウンロード数・伸び率 / GitHub のスター / 英語記事での言及回数 | npm registry, GitHub API, 過去 90 日のダイジェスト |
| 国内の厚み | Qiita の記事数 / Zenn の記事数 / 日本語記事での言及回数 | Qiita API, Zenn API, 過去 90 日のダイジェスト |

差が無いもの（両方厚い）は既に知られているので紹介する価値がなく、
両方薄いものはまだ実体がありません。**差が大きいものだけ**を出します。

判定は 2 つに分けています。読者が言う台詞が違うので、根拠にする信号も変えています。

- **海外で先行** — 勢いで測ります。ダウンロードの伸び率・直近の英語圏での言及・更新の新しさ
- **静かに使われている** — 定着で測ります。話題性ではなく、実際に使われている量そのもの

### 話題性を LLM に聞きません

ここが設計上いちばん大事な点です。「これは海外で話題ですか」と聞けば答えは返ってきますが、
それは**学習時点の記憶であって現在の観測ではありません**。数えるのはこちら側の仕事で、
LLM に任せているのは 2 か所だけです。

1. **名前の同定** — 語が「導入して使える道具」かの判定と、npm パッケージ名・GitHub リポジトリの特定
2. **紹介文** — 同僚に言う一言、置き換え対象、効く場面、注意点

紹介文には**数字を書かせていません**。実測値と食い違ったものが画面に並ぶと、
読者はその数字を持って人に話しに行くことになります。数字は計測値から機械で組み立てます。
評価語（すごい・便利・爆速・話題の）も禁止しています——評価は聞いた相手がするもので、
読者が言えるのは「何ができるか」だけです。混ぜた紹介は聞いた側から見ると中身がありません。

### 間違った数字を出さないための仕掛け

この枠の壊れ方は 1 つだけで、**間違った数字を持って人に話しに行くこと**です。
だから計測側に検証を重ねています。

- **npm パッケージの実在確認** — 名前解決は LLM なので、存在しない名前が返ります（実測で
  「TanStack Table」に `@tanstack/table` が割り当てられ 404 でした）。確認せずに進むと、
  ダウンロード数だけが欠測した顔でカードが出て、npm への死んだリンクが並びます
- **取り違えの検出** — 実在するが別のパッケージ、という場合は 404 では防げません
  （「TanStack Router」に `@tanstack/router` が割り当てられ、それは 0.0.1-beta.53 で
  止まった別物でした）。手がかりはダウンロード数とスター数の比で、スターは 1 人 1 回しか
  増えないのに対しダウンロードは使うたびに増えるので、**実際に使われているライブラリでは
  必ずダウンロードが上回ります**。下回っていたら信用できない数字として捨てます
- **測った対象を隠さない** — パッケージ名とバージョンを画面に出します。機械で見分けられない
  取り違えは、目で見分けられる形にしておくしかありません
- **非推奨・アーカイブ済みを落とす** — 紹介した後に「それ deprecated ですよ」と返されるのは
  致命的なので、判定の最初で落とします
- **数え切れなかった数字で「薄い」と言わない** — 「日本語ではまだ薄い」は**上限の主張**です。
  Zenn の検索は 1 ページ 48 件までしか数えられないので、収まらなかったときの件数は
  下限値でしかありません。上から抑えられない数字は根拠に使いません
- **「測れなかった」と「0 だった」を混同しない** — 「Qiita に 1 本も無い」は強い主張ですが、
  欠測をそう扱うと存在しない発見を報告することになります

### 母集団は追加の収集をしません

候補になる道具の名前は、**過去 90 日のダイジェストの `keywords`**（要約段で固有名詞優先で
抽出済み）と、**当日の GitHub 急上昇リポジトリ**から取ります。毎日ダイジェストを作った
副産物として溜まるものなので、新しい収集はゼロです。

計測だけが外部 API を叩きます。1 語あたり最大 4 リクエスト（Qiita / Zenn / npm / GitHub）で、
`config/radar.json` の `measureBudget`（既定 20）で 1 日の語数を抑えています。
一度計測した語は `remeasureAfterDays`（既定 14 日）まで測り直しません。

**効くのは Qiita の上限です。未認証は 60 リクエスト/時**で、実測ではこれに簡単に当たります
（当たると 403 が返り、国内の記事数が測れないので**その語はその日の判定を保留します**——
盤面には出ませんが、間違った数字が出ることもありません。翌日に測り直します）。
`QIITA_TOKEN` を登録すると 1000 リクエスト/時になるので、**この機能を使うなら登録しておくのが
実質必須**です。半分以上の語で取得できなかった実行では、その旨が画面の冒頭に出ます。

結果は `data/radar-ledger.json` に台帳として貯まります。役割は 3 つです。

- 名前解決の結果を貯めて、同じ語に二度と LLM を使わない（**「道具ではなかった」という否定の
  結果も貯めます**。実測では候補 73 語のうち 16 語が概念・機能名でした）
- 再計測の間隔を管理して、外部 API の呼び出し数を一定に保つ
- 計測の履歴を残して、自分のデータで伸びを見られるようにする

台帳は**ブラウザからは読みません**。語が増える一方のファイルで、画面に出るのは 10 件だけです。

### Qiita の数え方を名前で切り替えます

既定はフレーズ検索（`"Oxlint"`）で、「その道具の名前が出てくる記事」を数えます。
専用記事だけを数えると過小になり、「まだ誰も知らない」と誤って言ってしまうためです。

ただし道具の名前が英語の一般語と同じ綴りのときは、これが使えません。実測で
**`Effect` のフレーズ検索は 12,342 件**で、ほぼ全部が CSS のアニメーションの記事でした
（タグ検索なら 31 件）。そこで名前解決のときに「一般語と同じ綴りか」も判定させ、
そうであればタグ検索（完全一致）に切り替えます。どちらで数えたかは画面にも出します。

## どう選んでいるか

```
収集(600件前後) → 重複排除 ─┬→ リリース情報を抽出（順位なし・全件）
                             └→ 3 レーンに振り分け（各 50 件）
                                 → レーンごとに Haiku 4.5 で採点
                                 → 各レーンのベストを Sonnet 5 で深掘り

イベント収集 → 期間・距離・関心で絞る（全部ルールベース）
                                 → 登壇募集だけ Haiku 4.5 で判定
```

コミュニティ情報は上の流れに合流しません（開催日と締切で引くので、収集した記事も
重複排除も使いません）。収集と並列に走り、片方が落ちてももう片方は出ます。

1. **重複排除** — URL 正規化・タイトル近似・過去に掲載済みの URL の 3 段階。同じ記事が翌日以降に再浮上しません
2. **事前スコアリング** — トピック適合度（68%）+ 人気度（22%）+ 一次情報ボーナス。ただしこれは**レーン振り分けの一材料**で、絞り込みの主軸ではありません
3. **レーン振り分け** — 目的ごとに別の信号で候補を選びます（下記）。ここはすべてルールベースで、API 費用はかかりません
4. **LLM 採点** — レーンごとに**別の問い**で 0〜100 点。同じ記事でも問いが違えば点は違います
5. **多様性の確保** — レーンごとに枠を確保します
6. **深掘り** — 本文を取得して、**レーンごとに違う項目構成**のカードに変換します（下記）

### 「今日読む価値」だけで選ぶと偏る

素直にスコア順で選ぶと、実測で深掘り枠が 2 日とも AI ツールの使いこなし Tips で
埋まりました（「Claude Code のトークン節約術」「サブエージェント並列はお得か」など）。
同じ日に出ていた Vite 8 や TypeScript の言語機能は下に沈み、公式ブログ 22 フィードから
毎日 40 件拾っているのに、上位 15 件に残る一次情報は 0〜1 件でした。

母集団が AI 一色（Qiita の新着がそうなっている）で、かつ「今日役に立つ」と
「長く効く」が別物なのが原因です。5 つの対策を入れています。

**① 陳腐化しにくさ（durability）を採点軸に足す**

各記事に「この情報が何年もつか」を判定させています。有用さとは別の軸です。

| 値 | 対象 | 目安 |
| --- | --- | --- |
| `foundational` | 言語仕様・Web標準・ブラウザ実装・プロトコル・アルゴリズム | 数年 |
| `durable` | ライブラリのメジャー変更・設計や運用の知見・障害の事後分析 | 1年 |
| `ephemeral` | 特定ツールの今の使いこなし・回避策・「試してみた」 | 数週間〜数ヶ月 |

AI を狙い撃ちにしないのが要点です。新モデルの能力変化や MCP のようなプロトコルの
話は `durable` 以上に、AI 以外でも「〇〇を導入してみた」は `ephemeral` になります。

**② ベスト N に枠を確保する**

スコア順で埋めたあと、満たしていない枠だけ下位と入れ替えます。
確保したいものは目的によって違うので、枠もレーンごとに変えています。

| レーン | 確保する枠 |
| --- | --- |
| 知る | **一次情報**（公式ブログ・リリースノート・CHANGELOG）/ **長く効くもの** |
| 作る | **今日試せるもの**（`payoff=apply` またはリポジトリ由来）/ **長く効くもの** |
| 話す | なし（争点があるかは採点で見ており、それ以上に決められる軸が無いため） |

入れ替えは下位からで、**1 位は必ず残します**。その日の最重要が枠確保で押し出されるのは
本末転倒だからです。候補がいない日はそのルールを諦めます（件数は減りません）。
確保できなかった日は実行ログに警告が出ます。

**③ 目的（レーン）ごとに別々の枠を与える**

以前は AI とそれ以外で分けていましたが、これは母集団の偏りを均すための便宜的な分割で、
「読者が何のために読むか」とは対応していませんでした。実測では掲載 159 件のうち 43% が
単一プロダクトの話に寄り、AI 枠の 65% を占めていました。

ひとつの「価値スコア」に畳むと、いちばん測りやすい指標——このツールではキーワード一致——
だけが残ります。そこで目的を 3 つに分け、**別の証拠・別の採点基準・別の予算**を与えます。

| レーン | 判定軸 | 判定の問い |
| --- | --- | --- |
| **知る** | 影響範囲 × 取り返しのつかなさ | 「知らないまま1週間過ごしたとき、何を間違えるか」 |
| **作る** | 可能性の差分 × 触れる実体 | 「この前後で、作れるものの集合はどう変わったか」 |
| **話す** | 立場が割れること | 「反対の立場を、藁人形にせず1文で書けるか」 |

どのレーンの要件も満たさないものは**作る**に落ちます。自分のスタックの実装ノウハウは
ここに入ります。

事前フィルタも目的ごとに変えているのが要点です。

- **知る はトピック一致を使いません。** 大きな話題は読者の関心と独立に成立します
  （サプライチェーン攻撃もハードウェアの価格高騰も `topics.json` にありません）。
  関心一致を門番にしている限り、関心の外の重大事は構造的に拾えません。
  代わりに規模の語彙・複数プラットフォームでの同時浮上・話題性の絶対値で測ります。
- **作る は「今日動かせる形か」で測ります。** インストール手順・コマンド・リポジトリ本体が
  あるかを最大の重みにしています。このレーンの行動変容は「試したくなる」なので、
  試せる形をしているかがいちばん効く証拠です。
  > 以前はここに**「初出性」**（過去のダイジェストに出ていない語の割合）を置き、
  > 単独で最大の重みを与えていました。**あれは新しさではなく無名さを測っていました。**
  > 無名な語だけで構成されたタイトル——個人の小さなリポジトリ——が満点を取り、
  > 有名なツールの重要なリリースは語が既知なので沈みます。実測でベストの 1 位が
  > 誰も知らない個人リポジトリになったのはこれが原因で、「出たことのない単語だから
  > 価値がある」という前提そのものが成り立っていませんでした。削除しました。
- **話す は discussion の量比で測ります。** 賛同だけなら star が伸びてコメントは伸びず、
  立場が割れるとコメント側が伸びます。語彙より信頼できる論争の検出器です。
  このレーンでは一次情報を優遇しません（公式のリリースノートに意見は書けないため）。

枠が埋まらないレーンは、そのレーンのスコア順で他から補充します。空になるのは
「その日は該当が無かった」のではなく「しきい値がずれていた」可能性が高く、
LLM に見せる前に枠を捨てるとその区別がつかなくなるためです。中身が薄いままだった場合は、
採点後のスコア下限（`MIN_TOP_SCORE` / `MIN_OTHER_SCORE`）で落ちます。

> `TOP_N` は**レーンごとの件数**です。既定は 2（深掘り 6 件）。
> 深掘りは Sonnet を使う一番高い工程で、実測でも費用の 6〜7 割を占めます。
> コストを戻したいなら `TOP_N=1`（3 件）にしてください。

**④ カードの項目構成をレーンごとに変える**

以前は全部のカードが同じ項目（何ができるようになるか / 何が変わるか / 試し方 /
なぜ重要か / 注意点）でした。ですが**「何が変わるか」と「何ができるようになるか」は
同じ差分を二度書いていました。** 3 レーンとも見ているのは同じ差分で、見る向きが
違うだけなので、レーンごとに 1 項目へ統合しています。

| レーン | 差分をどの向きから見るか | 統合後の項目 |
| --- | --- | --- |
| 知る | 自分への影響として | **関係がある人** |
| 作る | 可能性の広がりとして | **できるようになること**（「これまで◯◯ → これから△△」の形） |
| 話す | 差分ではなく立場の対立なので持たない | — |

共通で持つのは `summary` / 前提知識 / 図 / コード / 関連リンク / 読了目安です。

**⑤ 図は「何を図にするか」を先に決めさせる**

図は 4 形式あり、**記事のいちばん重要な構造を 1 つだけ**選ばせます。

| 形式 | 何を担当するか |
| --- | --- |
| **構成図**（`architecture`） | **何がどこを経由してどこへ届くか。** 層を上から下へ 2〜4 段積み、層の間に「何が渡るか」を書きます |
| 流れ（`flow`） | **時間の順序があるもの。** 事故が起きた経緯、移行のスケジュール、手順 |
| 対比（`comparison`） | 二つの状態の対比。変更前と変更後、賛成側と反対側 |
| 実測値（`metrics`） | 記事に実際の数値があるときだけ |

要点が 2 つあります。

- **「箇条書きの言い換えなら図を作らない」を明示しています。** 実測で、`comparison` の
  4 行が「関係がある人」4 項目とほぼ同じ内容になっている日がありました。読者は同じことを
  2 回読むだけなので、その場合は図を出しません（`null`）。図の各行が箇条書きのどれかと
  同じことを言っていないか、書いたあとに照合させています
- **構成図は自由なグラフにしていません。** 任意の位置にノードを置いて矢印で結ぶには
  座標かレイアウト計算が必要で、線が交差した瞬間に読めなくなります。記事に出てくる構成の
  ほとんどは「呼ぶ側 → 経由するもの → 実体」の層で表せるので、**層に限って描画が
  必ず一意に決まる**ようにしました。狭い画面でも層の中で要素が折り返すだけで崩れません。
  記事が論じている当のものには印が付くので、「この記事は構成のどこの話か」が分かります

各レーンには**カードの中心の問い**があります。目的とする行動変容から逆算したものです。

| レーン | 行動変容 | カードの中心の問い |
| --- | --- | --- |
| 知る | 確認したくなる | 「これを知らないまま1週間過ごしたとき、何を間違えるか」 |
| 作る | 試したくなる | 「これは自分に関係があるか。あるなら、どう始めるか」 |
| 話す | **発信したくなる** | 「この争点に、自分の経験から何を足せるか」 |

| 知る | 作る | 話す |
| --- | --- | --- |
| 関係がある人 | できるようになること | 争点 |
| いつから | 使える場面 | 一次情報を出すとしたら？ |
| 必要なアクション | 向かない場面 | 確かめられること |
| まだ確定していないこと | 試し方 | |
| | 注意点 | |

要点が 6 つあります。

- **知るの箇条書きは読み物ではなく一覧表です。** 誰に・いつから・何をするかを目で拾える
  ことが価値なので、1 項目 1 行に制限し、理由や背景は `summary` に寄せています。
  「関係がある人」は**「〜な人」の形で淡々と並べる**だけにして、影響の内容は書かせません
  （「〜なので」「〜になる」が入ったら書きすぎ）。「いつから」には報道や資金調達の経緯を
  入れさせません——読者の期限だけを拾わせます
- **知るの「必要なアクション」は使い方の手順ではありません。** 読者が知りたいのは
  使い方ではなく自分がどう巻き込まれるかなので、「該当するか調べて対処する」側を書きます
- **知るの「まだ確定していないこと」は、進行中の事象で推測を確定として読ませないための枠**です。
  ここを空にしたまま推測を「関係がある人」に混ぜるのが、このレーンで一番まずい壊れ方です
- **作るの「できるようになること」は、仕組みではなく絵が浮かぶ具体を書かせます。**
  中心の問いは「読んだ人が『そんなことができるのか、試したい』と思うか」です。
  実測で「CAD 編集を MCP 経由のエージェントにも型付き・承認制で開放できる」のような
  仕組みの列挙が返っていました——正しいのですが、これを読んで手は動きません。
  ✓「ブラウザを開くだけで 3D 部品を設計して、STEP で書き出せる」の側に寄せ、
  1〜2 個・各 45 字に絞っています（付随機能を並べると、どれが本体か分からなくなります）
- **作るの「注意点」は最重要の 1 つだけにします。** 実測で 2 件返ってきていましたが、
  「非推奨警告あり」「上限はモデル構造依存」のような**仕様の細部**が混ざり、本当に詰まる
  1 件が埋もれていました。「知らずに始めると詰まる / 想定外に金がかかる / 壊れる」の
  どれかに当たるもののうち、いちばん起こりやすく損害が大きい 1 つだけを書かせます。
  仕様の細部は「使える場面 / 向かない場面」か「試し方」に属します
- **作るの「使える場面 / 向かない場面」は判定できる条件だけにします。** 以前は
  「向いている場面 / 向いていない場面」で、返ってくるのは「効率化したい開発者に向いている」
  のような人物像でした。それは誰にでも当てはまるので判定に使えません。
  **読者が自分の環境を見て YES / NO で即答できる条件**（「CI のビルドが 5 分を超えているとき」
  「Windows で動かすとき（未対応）」）だけを書かせ、試し方より上に置いています——関係の
  有無を先に決められないと、手順があっても試されないためです
- **話すの「争点」は、論点ごとの対で持ちます。** 以前は「賛成側の根拠」と「反対側の根拠」を
  **別々の平行なリスト**（各 2〜4 項目）にしていました。読者が頭の中で対応づけないと
  噛み合いが見えず、実測では**対応していない項目も混ざっていました**——記事と同じ立場の
  補強が「反対側の根拠」に入っていた日がありました。議論の形は「A と言われるが B だ」という
  噛み合いなので、論点ごとに「こう言われる / こう返せる」を対にします。
  成り立つ条件・崩れる条件は独立させず、この対の中に入れます（「小規模なら前者、
  CI が遅いチームなら後者」）——条件を別項目にすると立場から切り離されるためです
- **話すの「一次情報を出すとしたら？」が中心の問いに直接答える項目**です。以前は
  「語れる角度」で切り口の名前だけを並べていました。凝縮されてはいましたが、
  `変更コストの高い境界の選別` と渡されても、読者は自分が何を言えるか分かりません。
  **発信の最大の障壁は「これを自分が言っていいのか」**なので、切り口と
  **「なぜ自分がそれを言えるのか」を対**にしました

**削った項目**

- **`headline`**（サイト側で付けていた 40 字の見出し）— `oneLiner`・3 行要約・`summary` に続く
  4 つ目の要約でした。実測で 1 つの事実が 1 枚のカードの 5 箇所に書かれていたので、
  カードの見出しは元記事のタイトルそのものにしています
- **知るの「知らないと何を間違えるか」/ 作るの「既存の何を置き換えるか」**（`whyItMatters`）—
  どちらも `summary` と重複していました。話すの「なぜ今この争点か」だけは争点の背景という
  別の情報を持っているので残しています

- **話すの「確かめられること」は 0〜2 個に絞ります。** 主張の真偽を自分の環境で
  検証する手順です。価値はありますが、確かめてから発信すると翌日以降になるので、
  発信の障壁を下げる 2 項目より下に置いています

**削った項目**

- **`headline`**（サイト側で付けていた 40 字の見出し）— `oneLiner`・3 行要約・`summary` に続く
  4 つ目の要約でした。実測で 1 つの事実が 1 枚のカードの 5 箇所に書かれていたので、
  カードの見出しは元記事のタイトルそのものにしています
- **知るの「知らないと何を間違えるか」/ 作るの「既存の何を置き換えるか」/
  話すの「なぜ今この争点か」**（`whyItMatters`）— どれも `summary` か争点と重複していました
- **話すの「成り立つ条件・崩れる条件」** — 独立項目をやめ、「争点」の対の中に入れました

**⑥「話す」には足場を添える**

このレーンだけ、記事に**争点・両側の一番強い言い分・あなたが持っている材料**を添えます。
意見が出ない理由を分解すると、主張の理解 → 反対側の把握 → 自分の位置決め →
自分にしか書けない一点、の順にハードルが上がります。詰まるのは最後で、
「同意」「違うと思う」なら誰でも書けますが、それは投稿する価値がありません。

**意見の下書きは作りません。** 下書きを渡すと自分の言葉でなくなるうえ、裏を取っていない
文章がそのまま外に出ます。渡すのは足場だけです。記事が片側の立場しか書いていない場合は
反対側に「記事の外」と印がつきます——そのまま引用すると誤って紹介することになるためです。

カードの「一次情報を出すとしたら？」も同じ考えで、**切り口の側は名詞句だけにして
文にはしません。**

```
一次情報を出すとしたら？
・生成量とレビュー負荷の実測
  → Claude Code と Codex を業務で毎日動かしているので、境界を固めた前後で
    レビュー時間がどう変わったかを数字で出せる
・「1 PR = 1 論理変更」が実際に回るか
  → 自分のリポジトリで試して詰まった箇所を、一次情報として言える
```

切り口が文で返ってきたものは意見の代筆なので、生成側で落としています（句点で終わるもの、
「〜べき」「〜と言える」を含むものを除外）。根拠の側（→ の後ろ）は文でよく、
これは主題への意見ではなく読者自身の状況の説明なので、この判定は通しません。

## AI のコストがかかっている処理

LLM を呼ぶのは **7 か所だけ**です。ほかの工程（収集・重複排除・事前スコアリング・
リリースのグルーピング・イベントの絞り込み・**トレンドの集計**・図の整形・画面）は
すべてコード側で、API 費用はかかりません。

実測（2026-08-01、全 4 段が成功したラン）を現行設定に換算した内訳です。
（`digest-summary` と `digest-outlook` はこの実測より後に追加した段です。どちらも
生成済みの要約テキストを合成するだけの短い呼び出しで、1 リクエストずつしか呼びません）

| 段階 | 何をするか | モデル | リクエスト | 入力の主因 | 費用/日 | 割合 |
| --- | --- | --- | ---: | --- | ---: | ---: |
| `release` | リリース告知かの判定と要約 | Haiku 4.5 | 1 | 候補 30 件前後 × 抜粋 500 字 | $0.010 | 3% |
| `score` | 候補 150 件を 0〜100 点で採点（レーンごとに 3 回） | Haiku 4.5 | 9 | `LANE_CANDIDATES` × 3 ÷ `RANK_BATCH_SIZE` | $0.081 | 21% |
| `describe` | 要約・3行要約・分類・durability | Haiku 4.5 | 3〜4 | 上位 36 件前後 × 抜粋 700 字 | $0.053 | 14% |
| `deep` | ベスト N の深掘り（本文を読む） | **Sonnet 5** | `TOP_N`×2 | 本文 `BODY_CHAR_LIMIT` 字まで | **$0.214** | **55%** |
| `digest-summary` | 冒頭の3〜5行サマリーの合成 | Haiku 4.5 | 1 | ベスト N・リリース・その他の要約テキスト | 数厘 | <1% |
| `digest-outlook` | サマリー末尾「この先の見立て」1行 | **Sonnet 5** | 1 | 今日の要約テキスト + 直近 7 日分のサマリー | $0.030 | 8% |
| `community` | 登壇募集がまだ空いているかの判定 | Haiku 4.5 | 1 | 候補 30 件前後 × 抜粋 700 字 | $0.005 | 1% |
| | | | | | **$0.393** | |

`community` は候補が無い日は呼ばれません（0 円）。

月あたり **約 1,700 円**。**深掘りが 1 件 $0.053** で、ここだけ Sonnet を使うため
費用の 6 割弱を占めます。件数に比例するので、`TOP_N` が唯一の実質的なレバーです。

`digest-outlook` は入力こそ短いものの、見立ての質を落としたくないので
`SUMMARY_MODEL`（既定 Sonnet 5）を推論 effort 付きで 1 回だけ呼びます。
削るなら `SUMMARY_EFFORT=low`、それでも高いと感じるなら `RANK_MODEL` に寄せる余地があります。

### 効きの薄い節約案（検討済み）

| 案 | 削減 | 見送った理由 |
| --- | ---: | --- |
| プロンプトキャッシュ | 約 $0.02 | リクエスト間で共有される部分が小さい |
| `BODY_CHAR_LIMIT` 12,000→8,000 | 約 $0.03 | 深掘りの質が落ちる |
| `LANE_CANDIDATES` 50→35 | 約 $0.03 | 以前 46〜60 位からベスト入りした実績があり、取りこぼす |
| `SUMMARY_EFFORT` medium→low | 約 $0.06 | 深掘りはこのツールの中核 |
| 深掘りを Haiku に | 約 $0.16 | 質の低下が大きすぎる |

> ⚠️ **Sonnet 5 の $2/$10 は 2026-08-31 までの導入価格**です。9/1 以降は $3/$15 に戻り、
> 深掘りが 1.5 倍になって **1 日あたり約 $0.46** になります。
> 画面の「API 費用」は日付で単価を切り替えるので、9/1 以降も正しい額が出ます。

### 使用量の確認

各ダイジェストの `usage` に段階別の実測（リクエスト数・入出力トークン・費用）が
入っています。画面右下の「API 費用」にマウスを乗せると内訳が出ます。

**段階が欠けていたら、その段は落ちています。** 例外にならず静かにルールベースへ
フォールバックするので、`usage.stages` が揃っているかが一番早い健全性チェックです
（`community` は候補が無い日には出ません）。

## 別のモデル・別のプロバイダで試す

`RANK_MODEL` と `SUMMARY_MODEL` にモデル ID を入れると、**モデル ID で自動的に
プロバイダを振り分けます**（`gpt-*` なら OpenAI、それ以外は Anthropic）。
段ごとに混ぜられるので、「採点だけ安いモデル、深掘りは据え置き」も試せます。

### 本番（GitHub Actions）で切り替える

コード変更は不要です。**Settings → Secrets and variables → Actions** で:

| 種類 | Name | Value |
| --- | --- | --- |
| Secret | `OPENAI_API_KEY` | `sk-...` |
| Variable | `RANK_MODEL` | `gpt-5.6-luna` |
| Variable | `SUMMARY_MODEL` | `gpt-5.6-luna` |

Variable を消せば既定（Claude）に戻ります。`ANTHROPIC_API_KEY` は登録したままで
構いません。指定されたモデル ID 側のキーだけが使われます。

### 回す前に 10 秒で確かめる

プロバイダを替えたときの最初の関門は、**構造化出力のスキーマが受理されるか**です。
本番を 10 分回した末に落ちるより先に分かるよう、最小の呼び出しで本番と同じ形の
スキーマをすべて試せます。

```bash
OPENAI_API_KEY=sk-... RANK_MODEL=gpt-5.6-luna SUMMARY_MODEL=gpt-5.6-luna npm run check:llm
```

数円で終わります。これが通ってから本番を回してください。

### 同じ入力で A/B を取る

トレンド系のソースは実行のたびに中身が変わるので、そのまま 2 回走らせても
**モデルの差なのか母集団の差なのか分かりません**。収集結果を固定して比べます。

```bash
export SP=/tmp/exp && mkdir -p $SP
export COLLECT_CACHE=$SP/input.json          # 1 回目に作られ、2 回目以降は再利用

ANTHROPIC_API_KEY=... GITHUB_TOKEN=$(gh auth token) \
  npm run collect -- --out $SP/A.json
OPENAI_API_KEY=... GITHUB_TOKEN=$(gh auth token) \
  RANK_MODEL=gpt-5.6-luna SUMMARY_MODEL=gpt-5.6-luna npm run collect -- --out $SP/B.json

npm run compare -- $SP/A.json $SP/B.json
```

`--out` は `data/` を触らないので、実験しても本番データは汚れません。
`compare` は段階別の費用と実行時間、同じ記事に対する判定の一致率
（category / lane / payoff / durability とスコア差）、ベスト N の入れ替わり、
3行要約の文面の見比べを出します。

> 費用を比べるなら**両方とも API キー経由**で実行してください。
> `LLM_BACKEND=claude-code` は従量課金がないので費用が $0 になり、比較になりません
> （`compare` が警告を出します）。

> `SUMMARY_EFFORT` は Anthropic のモデルにしか効きません。`gpt-5.6-luna` で
> `reasoning_effort` が使えるか確認できなかったため、推測でパラメータを送っていません。
> 深掘りの比較は Claude 側がやや有利な条件になります。

## 画面の使い方

- **今日のサマリー** — ページ冒頭に、その日の技術界隈の傾向を3〜5行で書いた
  インサイトが出ます。「セキュリティ関連の修正が多かった」「AI関連の新機能公開が
  続いた」のように、個々の記事の紹介ではなく複数項目を束ねた傾向を LLM が書きます。
  ベスト N・リリース情報・その他の注目記事の要約と、分野・カテゴリ・リリース内訳の
  集計から合成します（生成済みの要約から作るだけなので追加費用はごく僅かです）
- **この先の見立て** — サマリーの最後に一行だけ、いま業界がどの局面にいて、
  この先どこへ向かいそうかを置きます。今日の材料に加えて**直近 7 日分のサマリー**を
  渡し、点ではなく流れとして読ませています。ここだけは推測なので、上の行と
  区切って出し、「〜になりそう」のように推測と分かる語尾で書かせています
- **目次** — ページ冒頭に件数付きのページ内リンクがあります
- **ベスト N のカードは畳んであります。** タップ/クリックで開きます。
  畳んだままでも元記事タイトル・3行要約・所要時間が見えるので、
  開く前に読むかどうか決められます
- **要約は 2 種類あります。** 同じ記事を二度書かないよう、**書く言葉づかいで役割を分けています**
  - **3行で要約**（畳んだ状態と一覧に出る）— 専門用語・略語・API 名を**一切使いません**。
    製品名も主題の特定に要るものだけ。開かなくても記事の話が分かることだけを引き受けます。
    **1 項目 1 文・句点で終わる・35 字以内**の 3 項目にしています——1 項目に 2 文詰めると
    画面で 3 行に収まらず、「3 行で読み切れる」という約束が崩れるためです
  - **カードを開いた冒頭の要約** — 逆に**記事の語彙をそのまま使って詳しく**書きます。
    分からない語はその場で開けるので（下の「前提知識」）、易しくする必要がないためです
- **前提知識はその場で開けます。** 本文中の語に点線と `?` が付いていたら、
  タップ/クリックでその語の説明が出ます。畳んだ「前提知識」一覧からも読めます
- **「◆ 話題」** — はてなブックマークのホットエントリーに載った記事、または
  そのプラットフォームのその日として明確に伸びている記事に付きます。
  他のエンジニアとの共通の話題になりやすい、という目印です
- **サムネイル画像は出る日と出ない日があります。** 元記事が配信している画像（OGP）のうち、
  **記事タイトルを絵にしただけの自動生成カードを落として**、書き手や編集部が自分で置いた
  画像だけを出しています。直近 10 日・58 件で調べたところ og:image の 7 割が Qiita・Zenn・
  GitHub の自動生成カードで、描かれていたのは見出しにすでに出ている文字でした。
  結果、画像が付くのは 6 件中 1 件前後です。画像はこのリポジトリに取り込まず配信元を
  直接参照しているので、向こうが消せば画像も消え、そのカードは画像なしの表示に戻ります
- **記事の中の画像は、解説の中で引用します。** 要約の直後に「記事の中の画像」として、
  書き手が説明のために置いた画像——実行結果のスクリーンショット、構成の図解、計測のグラフ——を
  最大 2 枚まで出します。**カード上部のサムネイルとは役割が違い、こちらは読むための画像**なので、
  何を見ればいいかを書いたキャプションを画像の下に付けています。
  バッジ・アバター・アイキャッチのような装飾は収集側で落とし、残ったものから
  「文章にするより画像のほうが早いもの」だけを AI が選ぶので、**引用が付かない記事のほうが多い**です
- **知る / 作る / 話す** — 「その他の注目記事」はタブで切り替えます
- **動いている話題の帯** — サマリーの直下に、いま動いている話題のチップが並びます。
  タップでトレンドタブへ。**今日ぶんを見ているときだけ出ます**（盤面が日付を持たないため、
  過去日に出すと嘘になります）
- **トレンド**（別タブ） — 話題ごとの現在地です。順位は付けません。
  - **今日動いた / 追跡中 / 落ち着いた** の 3 つ。動いた話題だけ見れば追いつけて、
    落ち着いた話題は追うのをやめられます
  - カード 1 枚が 1 つの話題。見出しの下に実際に出た表記（`Cursor` の下に `Cursor Origin`）、
    初出日・累計・今日の本数、直近 14 日のスパークラインが出ます
  - **タイムラインの記事には掲載の印が付きます**（`知る 1位` / `リリース` / `未掲載`）。
    自分が見た地点からの差分だけを追えるようにするためです。既定は日付の違う 3 件で、
    残りは「他 N 本を見る」で開きます
  - **★** を押すとその話題が帯の先頭に来ます。この端末にだけ保存されます
- **コミュニティ**（別タブ） — 読者が最初に知りたいのは「いつか」なので、日付を主役にしています。
  - 先頭は **応募の締切**。残り日数を大きく出し、3 日以内は色が変わります
  - その下に **3 週間の日付ストリップ**。何かある日にはドットが付き、土日は色が違い、
    今日は枠で囲みます。クリックでその日へ飛べます
  - 本体は**日付ごとのアジェンダ**。見出しは `8/16 (日) 3日後` のように相対でも読めます
  - 前回の盤面に無かったものには `NEW`、connpass 由来なら `満席（補欠12）` のように
    埋まり具合も出ます。**満席のものは行ごと薄くしています**（行けないものに時間を使わせないため）
- **「✳ Claude に聞く」** — その記事の文脈を積んだ状態で Claude の会話を開きます。
  ベスト N・その他の注目記事・リリース情報・検索結果の全部に付いています
- **「試し方」はそのまま貼れるプロンプト** — 作るレーンのカードの「試し方」は、コーディング
  エージェントに貼って試し始められる形で出ます。コピーと、開く先のボタンが付きます（PC は
  Claude Desktop / iximiuz Labs / Codespaces / Cloud Shell、スマホは Claude アプリ）。
  その他の注目記事・リリース情報・発掘の道具（GitHub / npm）にも同じものが畳んで付きます

## 「✳ Claude に聞く」の仕組み

`https://claude.ai/new?q=<プロンプト>` を開くだけです。API は使わないので**追加費用はゼロ**、
鍵の設定も要りません。ログイン済みの本人のアカウントでそのまま会話が始まります。

- **スマホ** — この URL は Claude アプリの Universal Link / App Link なので、
  アプリが入っていればアプリ側が開きます（入っていなければブラウザ）
- **デスクトップ** — claude.ai のリンクをデスクトップアプリに渡すことはできないため Web 版が開きます。
  そのため押した時点で**同じプロンプトをクリップボードにも入れて**います。
  デスクトップアプリで続けたいときは、アプリを開いて貼ってください
- **渡している中身** — タイトル・URL・出典・サイト側の要約・前提知識・争点・キーワード。
  そのうえで「原文を確認して 300 字で説明し、どこを掘りたいか選択肢にして聞いて」と頼んでいます。
  用途（使い方が分からない／用語が分からない／SNS に書きたい）は毎回違うので、
  ボタンは分けず、掘る方向は Claude 側から聞かせる形にしています
- **URL 長** — 日本語 1 文字が URL エンコードで 9 文字になるため、積めるのは 900 字弱です。
  上限（`web/src/askClaude.ts` の `MAX_ENCODED_LENGTH`）を超える分は、
  優先度の低い節から落とします（要約 → 前提知識 → 争点 → キーワード → 補足 の順に残す）。
  落ちてもクリップボード側には全文が入ります

## 「試し方」はそのまま貼れるプロンプト

読んだ道具を**自分で試す**までのハードルを下げるための形です。作るレーンのカードの
「試し方」は、箇条書きではなく、コーディングエージェント（Claude Code など）に
そのまま貼って試し始められるプロンプトとして出ます。

```
# 試すこと            ← 1 行の目標と、元の URL
# 手順                ← 番号付き。1 行 1 コマンドか 1 動作。人間しかできない手順は「（手動）」
# 確認したいこと      ← やってみないと分からないことだけ、1〜3 個
# 前提・注意          ← 必要な環境や鍵、記事本文でコマンドが欠けている等

---
~/lab/<リポジトリ名>/ を作業ディレクトリにして、その外は触らないで。
まず手順を読んで「何を・どの順で・何分で」を 3 行で提案し、私の OK を待ってから始めて。
…
```

上の 4 節は collector の LLM が記事から書きます（`deep.tryPrompt`。見出しと順番は
`collector/src/try-prompt.ts` の `TRY_PROMPT_HEADINGS` に固定してあり、崩れていれば null に
落とします）。`---` の下の**作業のさせ方はサイト側の固定文**です（`web/src/tryPrompt.ts`）。
記事に依存しないので、生成し直さずに変えられます。

### 開く先

プロンプトの下に「プロンプトをコピー」と、開く先のボタンが並びます。並ぶボタンは端末で違います。

**PC**（マウスのある画面）:

| ボタン | 何が開くか | プロンプト |
| --- | --- | --- |
| ▶ Claude Code で開く | Claude Desktop の Code タブを新しいセッションで（`claude://code/new?q=…`） | **入った状態で開く**。送るまで何も走らない。作業フォルダは開いたあとに選ぶ |
| ☁ iximiuz Labs | 使い捨ての Ubuntu（Claude Code 入り。無料枠は 1 日 1 時間） | 開いてから貼る |
| ☁ Codespaces | GitHub Codespaces の空の環境（永続。無料枠は 2 コアで月 60 時間） | 開いてから貼る |
| ☁ Cloud Shell | Google Cloud Shell（無料。週 50 時間） | 開いてから貼る |

**スマホ**: 「▶ Claude アプリで開く」の 1 つだけ。`https://claude.ai/code/new?q=…` は
Claude アプリの Universal Link / App Link なので、アプリが入っていれば Code タブが
プロンプト入りで開き、無ければブラウザで claude.ai が開きます。クラウドのセッションに
なるので、開いた先でリポジトリを選びます（Claude Code が使えるプランが必要です）。

URL でプロンプトを渡せるクラウド環境は無かったので、どのボタンも押した時点で
クリップボードに全文を入れます。長さの上限は、Claude Desktop のリンクが約 14,000 字
（余裕を見て 12,000 字で切る）、スマホの https リンクがエンコード後 8,000 文字
（日本語で 900 字弱）。超える分は後ろの節（前提・注意 → 確認したいこと）から落とします。
本文は 1,200 字に縛ってあるので、PC 側は通常当たりません。

環境ごとの開き方と初回の準備（ログイン、Claude Code のインストール）は、設定画面
（ロゴを 5 回叩く）の「ヘルプ」に書いてあります（`web/src/views/TryHelp.tsx`）。

`claude://` のリンクは Claude Desktop が入っていれば OS がアプリに渡します。ブラウザが
初回だけ「Claude を開きますか」と聞くので許可してください。リンク経由で渡した
フォルダは信用されない仕様なので、このサイトは `folder` を付けず、作業ディレクトリは
プロンプトの末尾で指示しています。

### 作るレーン以外にも付きます

その他の注目記事・リリース情報・発掘の**道具**（URL が GitHub リポジトリか npm を
指すもの）には、身元から機械的に組んだ同じ形のプロンプトが「⎘ 試すプロンプト」として
畳んで付きます（LLM を通さないので追加費用はゼロ）。記事（Qiita / Zenn / はてな / HN）
からは身元が取れないので付きません——記事であって道具ではないので、これは正しい挙動です。

この機能より前の日のカードには `tryPrompt` が無いので、`howToTry` の箇条書きを同じ
4 節に包んで出します。手順そのものが無いカードだけ、従来の箇条書きのままです。

## 関心トピックを変える

**サイトの「設定」画面から編集できます。** トピック名・重要度(1〜5)・キーワードを、タグ入力の UI で複数追加・削除できます。

設定画面はナビゲーションに出していません。開き方は 2 つです。

- **URL バーがある場合**: `https://<ユーザー名>.github.io/news-curator/#/settings` を直接開く
- **ホーム画面に追加した PWA の場合**: URL バーが無いので、ヘッダーの**ロゴマークを 3 秒以内に 5 回叩く**

読み手向けの画面ではないので導線を絞っているだけで、秘匿ではありません。
開いている間は `noindex, nofollow, noarchive` を立てています（ハッシュはサーバーに送られないため
そもそも別ページとしてインデックスされませんが、明示しています）。

収集処理は GitHub Actions 上で `config/topics.json` を読むので、編集内容は一度リポジトリへ
コミットする必要があります。手順は 3 ステップです。

1. **JSON をコピー** で画面の内容をクリップボードに取る
2. **GitHubで編集** で `config/topics.json` の Web エディタを開く
3. 貼り替えてコミットする（翌朝の実行から反映）

「読者プロフィール」欄も採点精度に直接効きます。使っている技術・立場・何に興味がないかを書くほど精度が上がります。

### 設定画面にアクセストークンは要りません

以前はブラウザに Fine-grained personal access token を貼って GitHub Contents API を
直接叩いていましたが、やめました。公開サイトの localStorage に write 権限付きの
トークンを常駐させる割に、書き込みの認可はリポジトリの権限そのもので足ります。
GitHub の Web エディタへ飛ばせば、ログイン済みで権限があれば編集でき、無ければできない。
リポジトリを private にしてもこの方式のまま動きます。

そのため設定画面には秘密が何もありません。訪問者が編集しても変わるのは
その人自身の localStorage だけです。タブから外しているのは安全のためではなく、
読み手に見せる必要がない画面だからです。

**過去にトークンを保存したことがある場合**、次にサイトを開いた時点で自動的に削除され、
その旨が画面に出ます。ただし削除しても失効はしないので、
[GitHub の設定](https://github.com/settings/personal-access-tokens)から revoke してください。

## 読者フィードバック（Good/Bad）で精度を上げる

ベスト N・その他の注目記事・リリース情報のすべての項目に Good/Bad を付けられます。
直近 14 日ぶんの投票をトピックの重みと LLM への読者コンテキストに反映し、
翌朝以降の採点に効かせます。**ボタンは通常は表示されません。** 認証は追加せず、
URL に秘密のパラメータを渡した本人のブラウザだけで表示を切り替えます。

- スマホでも同じ URL パラメータ方式で動きます（ブラウザは選びません）
- 一度開けば `localStorage` にフラグが残るので、以降は毎回パラメータ不要です
- 投票データは Firestore に保存し、**TTL で 14 日後に自動削除**されます。興味関心が
  変わっても古い投票が残り続けません
- ボタンを押していない大多数の訪問者は、フィードバック機能のコード（Firebase SDK）を
  一切ダウンロードしません（動的 import）

セットアップしなくてもツールは今まで通り動きます。未設定時は完全に無効化されます。

### セットアップ

1. [Firebase Console](https://console.firebase.google.com/) でプロジェクトを作成し、
   Firestore を **Native mode** で有効化する
2. プロジェクト設定 → アプリを追加 → ウェブアプリを登録し、`apiKey` / `projectId` / `appId` を控える
3. Firestore → ルール で以下を貼り付けて公開する

   ```
   rules_version = '2';
   service cloud.firestore {
     match /databases/{database}/documents {
       match /feedback/{articleId} {
         allow read, list, delete: if false;
         allow create, update: if isValidFeedback(articleId);

         function isValidFeedback(articleId) {
           let d = request.resource.data;
           return d.keys().hasOnly([
               'articleId','vote','votedAt','expireAt','digestDate','tier',
               'source','sourceLabel','category','lane','matchedTopics','score','title','url'
             ])
             && d.articleId is string && d.articleId == articleId
             && d.vote in ['good', 'bad']
             && d.votedAt == request.time
             && d.expireAt is timestamp
             && d.expireAt > request.time
             && d.expireAt < request.time + duration.value(15, 'd')
             && d.digestDate is string && d.digestDate.matches('^[0-9]{4}-[0-9]{2}-[0-9]{2}$')
             && d.tier in ['top', 'other', 'release', 'community']
             && d.source is string && d.source.size() < 40
             && d.sourceLabel is string && d.sourceLabel.size() < 80
             && d.category is string && d.category.size() < 40
             && (d.lane == null || d.lane in ['know', 'build', 'talk'])
             && d.matchedTopics is list && d.matchedTopics.size() <= 20
             && (d.score == null || (d.score is number && d.score >= 0 && d.score <= 100))
             && d.title is string && d.title.size() <= 300
             && d.url is string && d.url.size() <= 2000 && d.url.matches('^https?://.*');
         }
       }
     }
   }
   ```

   > **レーン導入前から使っている場合は、先にルールを更新してください。**
   > `hasOnly([...])` は許可する項目の**ホワイトリスト**なので、旧ルール
   > （`'domain'` が入っているもの）のままだと、`lane` を送るようになった
   > 新しい画面からの投票がすべて拒否されます。投票の失敗は `console.warn` に
   > 出るだけで画面には出ない（ボタンは押した色に変わる）ため、気づかないまま
   > Good/Bad が 1 件も貯まらない状態になります。
   >
   > 新旧どちらのサイトからの投票も落とさずに移行するには、**両方の項目を許可した
   > ルールを先に公開**してから、サイトをデプロイしてください。旧サイトは `domain`
   > だけ・新サイトは `lane` だけを送るので、**どちらも「無いことがある」前提で
   > 書く必要があります**。`d.domain` のような直接アクセスはキーが存在しないと
   > ルール評価がエラーになって拒否されるため、ここは `get()` を使います。
   >
   > ```
   >   'source','sourceLabel','category','domain','lane','matchedTopics','score','title','url'
   > ...
   >   && (d.get('domain', null) == null || d.get('domain', null) in ['ai', 'general'])
   >   && (d.get('lane', null) == null || d.get('lane', null) in ['know', 'build', 'talk'])
   > ```
   >
   > 新しいサイトからの投票が届いていることを確認したら、`'domain'` を落として
   > 上のルールに揃えます（その時点では `lane` は必ず送られるので直接アクセスで構いません）。
   >
   > なお `rules_version` はルール**言語**のバージョンで、`'2'` のまま変更しません。
   >
   > **`tier` に `'community'` を足すのも同じ話です。** コミュニティ情報より前の
   > ルール（`['top','other','release']`）のままだと、コミュニティ欄からの投票だけが
   > 静かに全部拒否されます。**ルールを先に公開してから**デプロイしてください。

   書き込みは投票本人のブラウザから直接行いますが、上のルールで
   `feedback` コレクションへの `create`/`update` 以外（読み取り・一覧・削除）を
   すべて拒否しています。`apiKey` などはこの設計では秘密情報ではありません
   （Firebase のアクセス制御はクライアントの鍵ではなくこのルール側で行います）。
   万一 URL の秘密パラメータが漏れても、実害はスパム投稿程度で、
   しかも 14 日で自動的に消えます。

4. Firestore → TTL で `feedback` コレクションの `expireAt` フィールドに
   TTL ポリシーを設定する（削除の反映まで最大 24 時間ほどかかります）
5. プロジェクト設定 → サービスアカウント → 新しい秘密鍵を生成し、JSON をダウンロードする
   （collector が読み取り専用でサーバー側から集計するために使います）
6. リポジトリの **Settings → Secrets and variables → Actions** に登録する

   | 種類 | Name | Value |
   | --- | --- | --- |
   | Secret | `FIREBASE_SERVICE_ACCOUNT_JSON` | ダウンロードしたサービスアカウント JSON の中身そのまま |
   | Secret | `VITE_FEEDBACK_TOKEN` | 自分だけが知る秘密の文字列 |
   | Variable | `VITE_FIREBASE_PUBLIC_API_KEY` | Firebase の apiKey |
   | Variable | `VITE_FIREBASE_PUBLIC_PROJECT_ID` | Firebase の projectId |
   | Variable | `VITE_FIREBASE_PUBLIC_APP_ID` | Firebase の appId |

   `PUBLIC` が付いている3つは名前の通り秘密にしなくてよい値です。Firebase の
   apiKey はアクセス制御に使われず（アクセス制御は前述の Firestore Security Rules
   が担う）、ビルド済み JS にそのまま入って誰でも見られる前提の値だからです。
   Secrets に入れても動作は変わりませんが、Variables の方が実態と一致します。

7. 使う環境ごとに一度だけ解除する。以降その環境では毎回 Good/Bad ボタンが表示されます

   - **URL バーがある場合**: `https://<ユーザー名>.github.io/news-curator/?fb=<VITE_FEEDBACK_TOKEN の値>` を開く
   - **ホーム画面に追加した PWA の場合**: 設定画面（ロゴマークを 3 秒以内に 5 回叩く）の
     「Good / Bad ボタン」で `VITE_FEEDBACK_TOKEN` の値を入力する

   解除の状態は localStorage に持ちます。iOS ではホーム画面に追加した PWA と Safari で
   保存領域が別々なので、Safari で解除しても PWA には引き継がれません。また PWA の
   起動 URL は manifest の `start_url` になり、`?fb=` を付けてホーム画面に追加しても
   クエリは残りません。PWA では後者の手順を使ってください。

### 反映のされ方

`collector/src/feedback.ts` が直近 14 日ぶんの投票をトピック名（`matchedTopics`）ごとに
集計し、少数の投票で重みが暴れないよう平滑化した上で

- `config/topics.json` の各トピックの重みに 0.75〜1.25 倍の乗数をかけて事前スコアリングに反映
- 変化の大きいトピック上位 3 件を一文にまとめ、LLM の採点・要約プロンプトに追記

します。Firebase を未設定のままにしておけば、この処理は丸ごとスキップされ、
今まで通りの動作になります（LLM バックエンド未設定時にルールベースへフォールバックするのと同じ考え方です）。

## 毎朝のプッシュ通知

ダイジェストが読める状態になったタイミング（Pages のデプロイ完了後）で、
購読した端末にプッシュ通知を送ります。通知をタップするとサイトが開きます。

- 購読は**端末（ブラウザプロファイル）ごと**です。設定画面（ロゴマークを 3 秒以内に
  5 回叩く）の「毎朝のプッシュ通知」から購読します
- **iOS は「ホーム画面に追加」した PWA の中でだけ**購読できます（iOS 16.4 以降）。
  Safari でサイトを開いただけでは通知 API 自体が生えません。Android は
  ブラウザのままで購読できます
- 購読情報（endpoint と暗号鍵）は Firestore の `pushSubscriptions` に保存します。
  読者フィードバックと同じく、書き込みはブラウザから直接・アクセス制御は
  Security Rules 側です。失効した購読（アプリ削除や許可の取り消し）は
  翌朝の送信時に自動で掃除されます
- 未設定ならこの機能は丸ごと無効になり、設定画面にも出ません

前提として、読者フィードバックのセットアップ（Firebase プロジェクトと
`FIREBASE_SERVICE_ACCOUNT_JSON` の登録）が済んでいる必要があります。
フィードバック機能自体（`VITE_FEEDBACK_TOKEN`）は解除していなくても構いません。

### セットアップ

1. VAPID 鍵ペア（プッシュサービスに対して送信者を証明する鍵）を生成する

   ```bash
   npm run push:keygen
   ```

2. リポジトリの **Settings → Secrets and variables → Actions** に登録する

   | 種類 | Name | Value |
   | --- | --- | --- |
   | Variable | `VITE_VAPID_PUBLIC_KEY` | 生成された Public Key |
   | Secret | `VAPID_PRIVATE_KEY` | 生成された Private Key |
   | Variable | `VAPID_SUBJECT` | （任意）`mailto:you@example.com` 形式の連絡先。未登録ならサイト URL が使われます |

   公開鍵はビルド済み JS に入る前提の値なので Variables でよく、秘密鍵だけが Secrets です。

3. Firestore → ルール に `pushSubscriptions` の match ブロックを**追記**して公開する
   （既存の `feedback` の match と並べて置きます）

   ```
   match /pushSubscriptions/{subId} {
     // endpoint は購読者以外に見せない。漏れると第三者がその端末へ通知を送れてしまう
     allow read, list: if false;
     // ドキュメント ID は endpoint の SHA-256。ID を知っている＝購読した本人の端末なので、
     // 解除（削除）はそのまま許す
     allow delete: if true;
     allow create, update: if isValidSubscription();

     function isValidSubscription() {
       let d = request.resource.data;
       return d.keys().hasOnly(['endpoint', 'p256dh', 'auth', 'updatedAt'])
         && d.endpoint is string
         && d.endpoint.matches('^https://.*')
         && d.endpoint.size() <= 2000
         && d.p256dh is string && d.p256dh.size() > 0 && d.p256dh.size() <= 300
         && d.auth is string && d.auth.size() > 0 && d.auth.size() <= 100
         && d.updatedAt == request.time;
     }
   }
   ```

4. 次のデプロイ後、受け取りたい端末で設定画面から「この端末で受け取る」を押す
   （iOS は先にホーム画面へ追加し、そのアプリの中で押します）

### 送られ方

`collector/src/send-push.ts` が毎朝のワークフローの最後（Pages デプロイ後）に走り、
当日のダイジェストから件数と読了目安を本文にした通知を全購読へ送ります。
通知が朝のうちに届かなかった端末（電源オフなど）では半日で破棄され、
翌日の通知だけが届きます（TTL 12 時間）。古い通知が夜中に鳴ることはありません。

手元から試し送りもできます（実際に全購読端末へ届くので注意）:

```bash
FIREBASE_SERVICE_ACCOUNT_JSON=$(cat service-account.json) VAPID_PUBLIC_KEY=... VAPID_PRIVATE_KEY=... npm run push:send
```

### API キーを使わずに生成する（ローカル開発用）

ログイン済みのローカル Claude Code CLI 経由で LLM を呼べます。API キー不要・従量課金なしで、
Claude Code のサブスクリプション枠で動きます（[ai-sdk-provider-claude-code](https://github.com/ben-vargas/ai-sdk-provider-claude-code) を利用）。

```bash

```

> [!IMPORTANT]
> **ローカル開発・検証専用です。** サブスクリプションの OAuth 認証は Claude Code と
> それをラップする層のためのもので、プロダクトの LLM バックエンドとして常用するのは
> Anthropic のポリシーに反します。CI で `LLM_BACKEND=claude-code` を指定すると
> 明示的にエラーで止まります。本番は必ず `ANTHROPIC_API_KEY` を使ってください。

技術的にも本番向きではありません。実測で比較すると:

| | Anthropic API 直接 | Claude Code CLI 経由 |
| --- | ---: | ---: |
| 入力トークン（採点150件） | 約 54,000 | 291,762 |
| 所要時間（全工程） | 約 30 秒 | 約 7 分 |
| 費用 | 約 $0.19 | $0（サブスク枠） |

エージェントハーネスを経由する分、トークンも時間も大きく増えます。プロンプトを
いじって出力を確かめる用途には十分ですが、毎朝の自動実行には向きません。

**LLM 側に必要なものはありません。** provider が依存する `@anthropic-ai/claude-agent-sdk` が
CLI を同梱していて、認証は macOS キーチェーンに保存済みの Claude Code のログインを使います。
`claude` コマンドが PATH に無くても（mise のシムが壊れていても）動きます。

別のビルドを使いたい場合だけ `CLAUDE_CLI_PATH` で実体を指定できます。

保存せずに結果だけ見る:

```bash
npm run collect:dry
```

過去の日付を指定する:

```bash
npm run collect -- --date=2026-07-30
```

サイトを開く:

```bash

```

http://localhost:5173/news-curator/ が開きます。`data/` と `config/` は dev サーバーが直接配信します。

## チューニング

環境変数（GitHub では **Settings → Secrets and variables → Actions → Variables**）で調整できます。

| 変数 | 既定値 | 説明 |
| --- | --- | --- |
| `RANK_MODEL` | `claude-haiku-4-5` | 採点に使うモデル。安さ優先 |
| `SUMMARY_MODEL` | `claude-sonnet-5` | 深掘りに使うモデル。`claude-opus-5` にすると品質は上がるがコストも上がる |
| `SUMMARY_EFFORT` | `medium` | 深掘りの思考量。`low`〜`max` |
| `TOP_N` | `2` | 深掘りする件数（**レーンごと**なので、2 なら計 6 件） |
| `KNOW_THRESHOLD` | `0.42` | 「知る」に振り分けるしきい値。実行ログの「振り分け」の行を見て調整します |
| `TALK_THRESHOLD` | `0.4` | 「話す」に振り分けるしきい値。同上 |
| `MIN_TOP_SCORE` | `45` | 深掘りするスコア下限。該当が乏しいレーンは件数が減ります |
| `MIN_OTHER_SCORE` | `30` | 一覧に載せるスコア下限 |
| `LANE_CANDIDATES` | `50` | 1 レーンあたりの採点候補数（合計は 3 倍） |
| `OTHER_N` | `12` | 「その他の注目記事」の件数 |

| `BODY_CHAR_LIMIT` | `12000` | 深掘り時に LLM へ渡す本文の最大文字数 |
| `CUTOFF_HOUR` | `7` | 集計の区切り時刻（JST） |

コストを下げたいとき — `SUMMARY_EFFORT` を `low` に、`OTHER_N` を減らす。
品質を上げたいとき — `SUMMARY_MODEL=claude-opus-5`、`SUMMARY_EFFORT=high` に。

`LANE_CANDIDATES` を絞るのは割に合いません。以前 45 まで下げる案を実データで検証したところ、
46〜60 位の帯に実際にベスト入りした記事が含まれていました。削減額は月 ¥80 程度です。

実際にかかった費用は毎回 `data/digests/YYYY-MM-DD.json` の `usage` に工程別で記録され、
サイト末尾にも表示されます。調整の判断はそちらの実測値を見てください。

**トレンドのしきい値は環境変数にしていません。** `collector/src/trends.ts` の冒頭の定数です。
母集団 572 件の実測に対して決めた値で、日々ひねるものではないためです
（各値をなぜその数にしたかはコメントに書いてあります）。


### 発掘のしきい値は `config/radar.json` で、単独で回して調整します

発掘のしきい値だけは環境変数ではなく `config/radar.json`（GitHub の Web エディタから
編集できます）に置いています。日次の収集ごと回さないと結果が見られないと調整できないので、
**発掘だけを単独で回すコマンド**を用意しています。発掘は記事のパイプラインに依存しない
（母集団は過去のインデックスと当日の GitHub だけ）ので単独で回せます。

```bash
npm run radar:dry
```

```bash
npm run radar:dry -- --thin=60 --budget=8
```

| 引数 | 用途 |
| --- | --- |
| `--thin=N` / `--known=N` | しきい値を仮に変えて結果を比べる（ファイルは書き換えません） |
| `--budget=N` | 計測する語数。外部 API の呼び出しを抑えたいとき |
| `--why=Oxlint` | ある語の台帳をそのまま出す。なぜ出ないのかを追うとき |
| `--save` | `data/radar.json` と台帳も書き換える |

出力には**盤面に載らなかったものとその理由**が必ず付きます。しきい値の調整では、
出たものより出なかったものの理由のほうが手がかりになります。

```
計測済みで盤面に載らなかったもの
  Electron                   日本語の記事が 3,865 本あり、日本でも既に知られている
  Biome                      日本語の記事が 506 本で、「まだ薄い」とは言えない
  request                    npm で非推奨として公開されている
```

`--save` を付けずに `--thin` を動かせば、外部 API を叩き直さずに（台帳の計測値を再利用して）
判定だけをやり直せます。

| 項目 | 既定値 | 説明 |
| --- | --- | --- |
| `domesticThin` | `100` | これ以下の記事数を「日本語ではまだ薄い」とみなす。上の較正表を基準に |
| `domesticKnown` | `400` | これを超えたら「もう知られている」として落とす |
| `measureBudget` | `20` | 1 回の実行で計測する語数。**`QIITA_TOKEN` を登録すれば 40〜60 まで上げられます** |
| `remeasureAfterDays` | `14` | 同じ語を測り直さない日数 |
| `minMentions` | `2` | 候補に入るのに必要な、過去 90 日での出現回数 |
| `adoption.npmWeekly` | `30000` | 「実際に使われている」と見なす週間ダウンロード数 |
| `adoption.stars` | `1500` | 同、スター数 |
| `limits.early` / `limits.hidden` | `5` / `5` | 盤面に載せる件数 |
| `exclude` | — | 常に外す語。**`topics.json` のトピック名とキーワードは自動で外れます**（自分で書いた関心リストは、定義上もう知っているものなので） |

## 保存されるデータ

| パス | 内容 |
| --- | --- |
| `data/digests/YYYY-MM-DD.json` | その日のダイジェスト全文（ベスト3の深掘り + リリース情報 + その他） |
| `data/community.json` | コミュニティの盤面。**日付を持たず、毎朝まるごと差し替わります** |
| `data/trends/board.json` | トレンドの盤面。同じく**日付を持たず、毎朝まるごと差し替わります** |
| `data/trends/YYYY-MM.json` | 話題台帳（日別の本数と母集団）。直近 28 日ぶんだけ残ります |


| `data/radar.json` | 発掘の盤面。日付を持たず、毎朝まるごと差し替わります |
| `data/radar-ledger.json` | 発掘の台帳（計測済みの語・名前解決の結果・計測履歴）。**ブラウザからは読みません** |
| `data/index/YYYY-MM.json` | 検索用の月別インデックス（タイトル・要約・キーワード・リンク） |
| `data/manifest.json` | 生成済みの日付・月の一覧と、生成元リポジトリ（設定編集リンク用） |

**コミュニティ情報はインデックスに入れていません。** イベントは開催が過ぎると価値がゼロに
なるので、入れると検索結果が終わったイベントで埋まります。履歴も持ちません
（`data/community.json` は毎朝上書きされます）。

検索画面はこの月別インデックスを読み込んで、タイトル・要約・キーワード・トピックを対象に AND 検索します。
すべて Git 管理なので、`git log data/` で履歴も追えますし、`grep` でも探せます。

### アーカイブが増えても重くならない仕組み

**読み込みの単位を表示の単位（1 ヶ月）に合わせています。** アーカイブ・検索はどちらも既定で
当月分だけを読み、何年分貯まっても 1 回の転送量は変わりません。

以前は全月をまとめて読んでいました。実測は **14.6KB/日・記事 25 件/日**（gzip で約 1/3.5）なので、
そのままだと 1 年で 5.2MB・13 リクエスト、3 年で 15.6MB・37 リクエストを毎回読むことになります。

検索の「全期間」を選んだときは、**1 リクエスト = 1 ヶ月のまま新しい月から順に**読み込み、
読めた分から結果に反映します。全部揃うのを待たないので、古い月が増えても最初の結果はすぐ出ます。

キャッシュについて。GitHub Pages は `cache-control: max-age=600` 固定で**変更できません**（`_headers` も使えない）。
代わりに、**過去月のインデックスと過去日のダイジェストは書かれた後は変わらない**ので `force-cache` で
転送ゼロで再利用しています。最新分だけ毎回検証します。履歴を作り直したときは
`web/src/api.ts` の `ARCHIVE_CACHE_VERSION` を上げてください（上げないと古いものが残ります）。

### 次の手を打つ目安

現状（1 日あたり index 14.6KB / ダイジェスト 215KB）から見た閾値です。

| 状態 | 到達時期の目安 | すること |
| --- | --- | --- |
| 1 ヶ月分の index が 1MB を超える | 記事数が 2 倍以上に増えたら | 検索用に `summary` を落とした軽量インデックスを別に作る |
| `data/` が 500MB を超える | 約 6 年 | GitHub Pages の 1GB 制限が近い。古いダイジェストを配信対象から外す |

`data/` は年 78MB ずつ増えますが、ダイジェストは**1 日 1 ファイルしか読まない**ので配信は何年でも問題ありません。
index を痩せさせる案は、占有が url 20% / summary 17% / title 15% / keywords 15% と分散していて
**支配的なフィールドが無い**ため、いま実施しても 2 割弱しか減りません（費用対効果が低いので保留）。

## 構成

```
collector/     収集・採点・要約（Node.js + TypeScript、GitHub Actions 上で実行）
web/           閲覧用の SPA（Vite + React、GitHub Pages で配信）
config/        トピック定義・監視対象・ソース定義・コミュニティの検索範囲・発掘のしきい値
data/          生成されたダイジェスト・検索インデックス・話題台帳・発掘の台帳
```

## 注意点

- GitHub Actions の cron は**数分〜十数分遅れることがあります**。収集と要約にも数分かかるため、7:00 ちょうどには更新されません。画面では「毎朝 8:00 までに」と案内しています
- リポジトリを private にすると GitHub Pages の配信に GitHub Pro が必要になります。無料のまま private にしたい場合は、配信先を Cloudflare Pages に変えてください（`BASE_PATH=/` を渡してビルドします）
- Zenn・はてなブックマークの API は非公式のため、仕様変更で壊れる可能性があります。1 つのソースが落ちても、他のソースだけで処理は続行します
- Doorkeeper の `events` は実測では未認証で読めますが、公式ドキュメントでは token 必須です。閉じられたら `DOORKEEPER_TOKEN` を登録してください
- confs.tech（`tech-conferences/conference-data`）は**海外中心のデータで、日本のカンファレンスはほとんど入っていません**。日本の CFP は connpass と、カンファレンス公式ブログの RSS（`watchlist.feeds`）に頼ることになります
- 発掘が使う Zenn の API（`/api/topics/*`・`/api/search`）と Qiita の `total-count` ヘッダは非公式・非文書化です。壊れたら国内の記事数が欠測になり、その語は「測れなかった」として盤面から落ちます（誤った数字が出るのではなく出なくなる側に倒しています）
- 発掘の計測は Qiita の API を 1 語 1 リクエスト使います。未認証は 60 リクエスト/時なので、`QIITA_TOKEN` を登録していない場合は `config/radar.json` の `measureBudget` を 20 以下にしてください（収集本体が Qiita を 8 リクエスト使います）
