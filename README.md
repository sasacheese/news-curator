# news-curator

関心のあるトピックの最新情報を、**毎朝 8:00 までに「前日 7:00 からの 24 時間」分だけ集めて、30 分でキャッチアップできる形に要約する**ツールです。

- 収集・要約は GitHub Actions が毎朝 7:00 JST に起動し、8:00 までに読める状態になります（PC を起動していなくても動きます）
- 結果は GitHub Pages の静的サイトで読みます（スマホからも見られます）
- 概要・リンク・キーワードは Git 管理の JSON に貯まるので、「あれ何だっけ」をあとから全文検索できます

サーバー費用は **0 円**（public リポジトリの GitHub Actions + Pages は無料枠）。かかるのは Claude API の実費だけで、**1 日およそ 20〜30 円 / 月 700〜900 円**が目安です。

---

## セットアップ

### 1. リポジトリを push する

```bash
git push -u origin main
```

### 2. Claude API キーを Secrets に登録する

[Anthropic Console](https://console.anthropic.com/settings/keys) で API キーを発行し、
リポジトリの **Settings → Secrets and variables → Actions → New repository secret** で登録します。

| Name | Value |
| --- | --- |
| `ANTHROPIC_API_KEY` | `sk-ant-...` |

> キーを登録しなくてもツールは動きますが、スコアリングがキーワードマッチだけになり、
> 「何ができるようになるか」「試し方」の解説は生成されません。

任意で、Qiita API のレート制限（未認証は 60 リクエスト/時）を緩めたい場合は `QIITA_TOKEN` も登録できます。

### 3. GitHub Pages を有効にする

**Settings → Pages → Build and deployment → Source** を **GitHub Actions** にします。

### 4. 最初のダイジェストを生成する

**Actions → Daily digest → Run workflow** を実行します。2〜3 分で
`https://<あなたのユーザー名>.github.io/news-curator/` にダイジェストが出ます。

以降は毎朝自動で更新されます（起動は 7:00 JST、読めるようになるのは 8:00 まで）。

## 何をどこから集めているか

前日 7:00 〜 当日 7:00（JST）に公開されたものだけが対象です。設定は 2 つに分かれています。

- `config/watchlist.json` — **どこを監視するか**（リポジトリ・フィード・CHANGELOG）。運用中に増減する部分
- `config/sources.json` — 各ソースの有効/無効と取得量のチューニング

| ソース | 内容 |
| --- | --- |
| Qiita | 全新着記事（LGTM・ストック数つき） |
| Zenn | daily トレンド + 新着 |
| はてなブックマーク | テクノロジーカテゴリのホットエントリー |
| Hacker News | 一定スコア以上のストーリー |
| dev.to | リアクション数の多い記事 |
| GitHub Releases | ウォッチ対象 35 リポジトリのリリースノート（React / Next.js / TypeScript / Vite / Prisma / Zod / TanStack / Playwright / Claude Code / Codex など） |
| GitHub 急上昇リポジトリ | 直近 3 週間に作られてスターを集めているリポジトリ |
| 公式ブログ RSS | Chrome Developers / web.dev / V8 / MDN / Node.js / TypeScript / React / Next.js / Vite / Vercel / GitHub / Cloudflare / Google Cloud / OpenAI など 22 フィード |
| CHANGELOG | Claude Code の CHANGELOG.md |

ソースそのものを止めたいときは `config/sources.json` の `enabled: false` を使ってください。

### 監視対象の追加・削除

`config/watchlist.json` の 3 つの配列を編集するだけです。ダイジェスト画面の「リリース情報」の下に
現在の監視対象一覧と **GitHubで編集** リンクがあるので、そこから Web エディタを開いて
コミットすれば翌朝の実行から反映されます（ローカルに clone しなくても、トークンを用意しなくても構いません）。

```jsonc
{
  // GitHub Releases を見るリポジトリ。owner/repo
  "repos": ["facebook/react", "vitejs/vite"],
  // RSS / Atom。weight は事前スコアの下駄（1〜5、既定 3）で、一次情報ほど高く
  "feeds": [{ "label": "React Blog", "url": "https://react.dev/rss.xml", "weight": 5 }],
  // リリースノートを持たず CHANGELOG.md だけ更新するもの。url は raw、homepage は表示用（省略可）
  "changelogs": [{ "label": "Claude Code", "url": "https://raw.githubusercontent.com/…/CHANGELOG.md" }]
}
```

書式を外した項目は警告を出してスキップし、URL の重複も落とします。1 行の typo でその日の収集が
丸ごと止まることはありません。実行ログの `監視対象: リポジトリ N / フィード N / CHANGELOG N` で
実際に読まれた件数を確認できます。

## リリース情報は別枠

新しい AI モデル・新 API・ライブラリの新バージョン・GA 昇格・新規公開などは、
**ランキングせずに全件**を別セクションに出します。読む価値の順位ではなく
「知っているかどうか」だけで差が出る種類の情報だからです。

### 並べる軸は「何ができるようになるか」

**メジャー / マイナー / パッチという分類では並べていません。** これは仕様上の分類で、
読み手の関心と一致しないからです。実測 27 件で確かめると:

| kind | 件数 | うち「できるようになる」系 |
| --- | ---: | ---: |
| service | 15 | 9 |
| patch | 5 | 2 |
| minor | 4 | **3** |
| ai-model | 3 | 3 |

`service` 15 件の中に「1 サンドボックスで複数エージェントを分離実行」と
「Server-Timing ヘッダーの通過」が同居し、`minor` のほうが打率が高い。
つまり分類の粒度と中身の大きさが対応していません。

そこで `impact`（読者に何が起きるか）を判定させて、それで並べています。

| impact | 見出し | 対象 |
| --- | --- | --- |
| `unlocks` | できるようになったこと | これまでできなかったことが可能になる |
| `security` | ふさがれた脆弱性 | 重大な脆弱性の修正 |
| `improves` | 速く・楽になったこと | 性能・コスト・DX の改善 |
| `chore` | 修正のみ | 新しくできることが増えない（**畳んで表示**） |

各項目には「**〜できるようになる**」の 1 行（`unlock`）を必ず書かせ、
書けなければ `chore` に落とします。分類だけ立派で中身が空、という状態を
構造で潰しています（「安定性が向上する」のような当たり障りのない文も弾きます）。

変化の大きさは形容詞では伝わらないので、読み取れたときだけ差分で見せます。

```
今まで   1 サンドボックスにエージェント 1 つ
これから 1 サンドボックスで複数エージェントを分離実行
```

対応範囲が広がったときは `scope` にバッジが出ます（`iOS` / `Android` /
`セルフホスト` など）。「スマホでも使えるようになった」を一目で分かるようにするためです。

### 脆弱性は別の入口から取る

**リリースノートには脆弱性が載りません。** 実測 27 件でセキュリティの言及は 0 件でした。
GitHub では脆弱性はリリースノートではなく Security Advisory として別に出るため、
監視対象を増やしても拾えません。

そこで [GitHub Security Advisories](https://docs.github.com/en/rest/security-advisories/global-advisories)
を別ソースにしています（認証不要・無料。`GITHUB_TOKEN` があればレート制限が 60/時 → 5,000/時）。

`config/sources.json` の `advisories` で設定します。

```jsonc
{
  "advisories": {
    "enabled": true,
    "severities": ["critical", "high"],
    "ecosystems": ["npm", "actions", "pip", "go"],
    // watchlist.json の repos から名前を導けないものを補う
    "extraPackages": ["@tanstack/react-router"]
  }
}
```

`watchlist.json` の `repos` からパッケージ名を導いて絞り込みます
（`facebook/react` → `react`、スコープ `@facebook/*`）。リポジトリ名とパッケージ名が
ずれるもの（`TanStack/router` の実体は `@tanstack/react-router`）は `extraPackages` に足してください。
**取得件数と採用件数は実行ログに出る**ので、取りこぼしていれば分かります。

LLM は通しません。GitHub が付けた深刻度・CVSS・修正版のほうが、要約より確かで有用です。

実装上の工夫が 3 つあります。

- **モノレポの一括リリースをまとめます。** 実測で `cloudflare/workers-sdk` が
  1 日に 12 パッケージ同時リリースしていました。リポジトリ単位で 1 件にまとめ、
  残りは「同じ製品の他 N 件」の折りたたみに入れます
- **同じ製品の複数告知をまとめます。** Vercel Changelog は 1 日に同じ製品の告知を
  何度も出します（実測で Vercel 4 件・GitHub Copilot 3 件）。同じ種類・同じ製品を
  1 件にまとめ、残りは同じ折りたたみに入れます。実測で 19 件 → 13 件になりました
- **公式ブログのリリース以外を除外します。** Vercel Changelog や GitHub Changelog には
  事業提携・料金改定・導入事例が混ざるので、LLM に判定させて落とします。
  ただし GitHub Releases と CHANGELOG は定義上リリースなので判定を待たずに採用します

リリース情報は深掘りカードにも入りえます（重大なリリースは深掘りする価値があるため）。
その場合は「上で詳説」の印がつき、「その他の注目記事」からは除外されます。

## どう選んでいるか

```
収集(600件前後) → 重複排除 ─┬→ リリース情報を抽出（順位なし・全件）
                             └→ 3 レーンに振り分け（各 50 件）
                                 → レーンごとに Haiku 4.5 で採点
                                 → 各レーンのベストを Sonnet 5 で深掘り
```

1. **重複排除** — URL 正規化・タイトル近似・過去に掲載済みの URL の 3 段階。同じ記事が翌日以降に再浮上しません
2. **事前スコアリング** — トピック適合度（68%）+ 人気度（22%）+ 一次情報ボーナス。ただしこれは**レーン振り分けの一材料**で、絞り込みの主軸ではありません
3. **レーン振り分け** — 目的ごとに別の信号で候補を選びます（下記）。ここはすべてルールベースで、API 費用はかかりません
4. **LLM 採点** — レーンごとに**別の問い**で 0〜100 点。同じ記事でも問いが違えば点は違います
5. **多様性の確保** — レーンごとに枠を確保します
6. **深掘り** — 本文を取得して、**レーンごとに違う項目構成**のカードに変換します（下記）

### 「今日読む価値」だけで選ぶと偏る

素直にスコア順で選ぶと、実測で深掘り枠が 2 日とも AI ツールの使いこなし Tips で
埋まりました（「Claude Code のトークン節約術」「サブエージェント並列はお得か」など）。
同じ日に出ていた Vite 8 や TypeScript の言語機能は下に沈み、公式ブログ 22 フィードから
毎日 40 件拾っているのに、上位 15 件に残る一次情報は 0〜1 件でした。

母集団が AI 一色（Qiita の新着がそうなっている）で、かつ「今日役に立つ」と
「長く効く」が別物なのが原因です。5 つの対策を入れています。

**① 陳腐化しにくさ（durability）を採点軸に足す**

各記事に「この情報が何年もつか」を判定させています。有用さとは別の軸です。

| 値 | 対象 | 目安 |
| --- | --- | --- |
| `foundational` | 言語仕様・Web標準・ブラウザ実装・プロトコル・アルゴリズム | 数年 |
| `durable` | ライブラリのメジャー変更・設計や運用の知見・障害の事後分析 | 1年 |
| `ephemeral` | 特定ツールの今の使いこなし・回避策・「試してみた」 | 数週間〜数ヶ月 |

AI を狙い撃ちにしないのが要点です。新モデルの能力変化や MCP のようなプロトコルの
話は `durable` 以上に、AI 以外でも「〇〇を導入してみた」は `ephemeral` になります。

**② ベスト N に枠を確保する**

スコア順で埋めたあと、満たしていない枠だけ下位と入れ替えます。
確保したいものは目的によって違うので、枠もレーンごとに変えています。

| レーン | 確保する枠 |
| --- | --- |
| 知る | **一次情報**（公式ブログ・リリースノート・CHANGELOG）/ **長く効くもの** |
| 作る | **今日試せるもの**（`payoff=apply` またはリポジトリ由来）/ **長く効くもの** |
| 話す | なし（争点があるかは採点で見ており、それ以上に決められる軸が無いため） |

入れ替えは下位からで、**1 位は必ず残します**。その日の最重要が枠確保で押し出されるのは
本末転倒だからです。候補がいない日はそのルールを諦めます（件数は減りません）。
確保できなかった日は実行ログに警告が出ます。

**③ 目的（レーン）ごとに別々の枠を与える**

以前は AI とそれ以外で分けていましたが、これは母集団の偏りを均すための便宜的な分割で、
「読者が何のために読むか」とは対応していませんでした。実測では掲載 159 件のうち 43% が
単一プロダクトの話に寄り、AI 枠の 65% を占めていました。

ひとつの「価値スコア」に畳むと、いちばん測りやすい指標——このツールではキーワード一致——
だけが残ります。そこで目的を 3 つに分け、**別の証拠・別の採点基準・別の予算**を与えます。

| レーン | 判定軸 | 判定の問い |
| --- | --- | --- |
| **知る**（画面では「潮目」） | 影響範囲 × 取り返しのつかなさ | 「知らないまま1週間過ごしたとき、何を間違えるか」 |
| **作る**（画面では「手札」） | 可能性の差分 × 触れる実体 | 「この前後で、作れるものの集合はどう変わったか」 |
| **話す**（画面では「論点」） | 立場が割れること | 「反対の立場を、藁人形にせず1文で書けるか」 |

どのレーンの要件も満たさないものは**作る**に落ちます。自分のスタックの実装ノウハウは
ここに入ります。

事前フィルタも目的ごとに変えているのが要点です。

- **知る はトピック一致を使いません。** 大きな話題は読者の関心と独立に成立します
  （サプライチェーン攻撃もハードウェアの価格高騰も `topics.json` にありません）。
  関心一致を門番にしている限り、関心の外の重大事は構造的に拾えません。
  代わりに規模の語彙・複数プラットフォームでの同時浮上・話題性の絶対値で測ります。
- **作る は「初出性」で測ります。** 新しさとキーワード一致は逆を向きます——新しい道具は、
  名前がまだどの語彙にも無いから新しいからです。過去のダイジェストに出てきた語を覚えておき、
  その補集合を「新しい」とみなします。
- **話す は discussion の量比で測ります。** 賛同だけなら star が伸びてコメントは伸びず、
  立場が割れるとコメント側が伸びます。語彙より信頼できる論争の検出器です。
  このレーンでは一次情報を優遇しません（公式のリリースノートに意見は書けないため）。

枠が埋まらないレーンは、そのレーンのスコア順で他から補充します。空になるのは
「その日は該当が無かった」のではなく「しきい値がずれていた」可能性が高く、
LLM に見せる前に枠を捨てるとその区別がつかなくなるためです。中身が薄いままだった場合は、
採点後のスコア下限（`MIN_TOP_SCORE` / `MIN_OTHER_SCORE`）で落ちます。

> `TOP_N` は**レーンごとの件数**です。既定は 2（深掘り 6 件）。
> 深掘りは Sonnet を使う一番高い工程で、実測でも費用の 6〜7 割を占めます。
> コストを戻したいなら `TOP_N=1`（3 件）にしてください。

**④ カードの項目構成をレーンごとに変える**

以前は全部のカードが同じ項目（何ができるようになるか / 何が変わるか / 試し方 /
なぜ重要か / 注意点）でした。ですが**「何が変わるか」と「何ができるようになるか」は
同じ差分を二度書いていました。** 3 レーンとも見ているのは同じ差分で、見る向きが
違うだけなので、レーンごとに 1 項目へ統合しています。

| レーン | 差分をどの向きから見るか | 統合後の項目 |
| --- | --- | --- |
| 潮目 | 自分への影響として | **誰に効くか** |
| 手札 | 可能性の広がりとして | **できるようになること**（「これまで◯◯ → これから△△」の形） |
| 論点 | 差分ではなく立場の対立なので持たない | — |

共通で持つのは `headline` / `summary` / 前提知識 / 図 / コード / 関連リンク / 読了目安です。

| 潮目 | 手札 | 論点 |
| --- | --- | --- |
| 誰に効くか | できるようになること | 賛成側の根拠 |
| いつから | 試し方 | 反対側の根拠 |
| 今日の確認 | 向いている場面 | 成り立つ条件・崩れる条件 |
| 知らないと何を間違えるか | 向いていない場面 | 語れる角度 |
| まだ確定していないこと | 既存の何を置き換えるか | 自分で確かめる |
| | 注意点 | なぜ今この争点か |

要点が 3 つあります。

- **潮目の「今日の確認」は手順ではありません。** 読者が知りたいのは使い方ではなく
  自分がどう巻き込まれるかなので、「試す手順」ではなく「該当するか調べる手順」を書きます
- **潮目の「まだ確定していないこと」は、進行中の事象で推測を確定として読ませないための枠**です。
  ここを空にしたまま推測を「誰に効くか」に混ぜるのが、このレーンで一番まずい壊れ方です
- **手札の「向いていない場面」は、新しい道具ほど書かれない項目**です。適用範囲が狭いことは
  弱点ではなく仕様なので、枠として持たせて記事から読み取らせます

**⑤「論点」には足場を添える**

このレーンだけ、記事に**争点・両側の一番強い言い分・あなたが持っている材料**を添えます。
意見が出ない理由を分解すると、主張の理解 → 反対側の把握 → 自分の位置決め →
自分にしか書けない一点、の順にハードルが上がります。詰まるのは最後で、
「同意」「違うと思う」なら誰でも書けますが、それは投稿する価値がありません。

**意見の下書きは作りません。** 下書きを渡すと自分の言葉でなくなるうえ、裏を取っていない
文章がそのまま外に出ます。渡すのは足場だけです。記事が片側の立場しか書いていない場合は
反対側に「記事の外」と印がつきます——そのまま引用すると誤って紹介することになるためです。

カード側の「語れる角度」も同じ考えで、**切り口の名前だけを並べて文にはしません。**

```
語れる角度
・40万件という母数の偏り
・見逃し率3倍という数字の測定条件
・自分のプロジェクトでの実測との差
```

文で返ってきたものは意見の代筆なので、生成側で落としています（句点で終わるもの、
「〜べき」「〜と言える」を含むものを除外）。

## AI のコストがかかっている処理

LLM を呼ぶのは **6 か所だけ**です。ほかの工程（収集・重複排除・事前スコアリング・
リリースのグルーピング・図の整形・画面）はすべてコード側で、API 費用はかかりません。

実測（2026-08-01、全 4 段が成功したラン）を現行設定に換算した内訳です。
（`digest-summary` と `digest-outlook` はこの実測より後に追加した段です。どちらも
生成済みの要約テキストを合成するだけの短い呼び出しで、1 リクエストずつしか呼びません）

| 段階 | 何をするか | モデル | リクエスト | 入力の主因 | 費用/日 | 割合 |
| --- | --- | --- | ---: | --- | ---: | ---: |
| `release` | リリース告知かの判定と要約 | Haiku 4.5 | 1 | 候補 30 件前後 × 抜粋 500 字 | $0.010 | 3% |
| `score` | 候補 150 件を 0〜100 点で採点（レーンごとに 3 回） | Haiku 4.5 | 9 | `LANE_CANDIDATES` × 3 ÷ `RANK_BATCH_SIZE` | $0.081 | 21% |
| `describe` | 要約・読みどころ・分類・durability | Haiku 4.5 | 3〜4 | 上位 36 件前後 × 抜粋 700 字 | $0.053 | 14% |
| `deep` | ベスト N の深掘り（本文を読む） | **Sonnet 5** | `TOP_N`×2 | 本文 `BODY_CHAR_LIMIT` 字まで | **$0.214** | **55%** |
| `digest-summary` | 冒頭の3〜5行サマリーの合成 | Haiku 4.5 | 1 | ベスト N・リリース・その他の要約テキスト | 数厘 | <1% |
| `digest-outlook` | サマリー末尾「この先の見立て」1行 | **Sonnet 5** | 1 | 今日の要約テキスト + 直近 7 日分のサマリー | $0.030 | 8% |
| | | | | | **$0.388** | |

月あたり **約 1,700 円**。**深掘りが 1 件 $0.053** で、ここだけ Sonnet を使うため
費用の 6 割弱を占めます。件数に比例するので、`TOP_N` が唯一の実質的なレバーです。

`digest-outlook` は入力こそ短いものの、見立ての質を落としたくないので
`SUMMARY_MODEL`（既定 Sonnet 5）を推論 effort 付きで 1 回だけ呼びます。
削るなら `SUMMARY_EFFORT=low`、それでも高いと感じるなら `RANK_MODEL` に寄せる余地があります。

### 効きの薄い節約案（検討済み）

| 案 | 削減 | 見送った理由 |
| --- | ---: | --- |
| プロンプトキャッシュ | 約 $0.02 | リクエスト間で共有される部分が小さい |
| `BODY_CHAR_LIMIT` 12,000→8,000 | 約 $0.03 | 深掘りの質が落ちる |
| `LANE_CANDIDATES` 50→35 | 約 $0.03 | 以前 46〜60 位からベスト入りした実績があり、取りこぼす |
| `SUMMARY_EFFORT` medium→low | 約 $0.06 | 深掘りはこのツールの中核 |
| 深掘りを Haiku に | 約 $0.16 | 質の低下が大きすぎる |

> ⚠️ **Sonnet 5 の $2/$10 は 2026-08-31 までの導入価格**です。9/1 以降は $3/$15 に戻り、
> 深掘りが 1.5 倍になって **1 日あたり約 $0.46** になります。
> 画面の「API 費用」は日付で単価を切り替えるので、9/1 以降も正しい額が出ます。

### 使用量の確認

各ダイジェストの `usage` に段階別の実測（リクエスト数・入出力トークン・費用）が
入っています。画面右下の「API 費用」にマウスを乗せると内訳が出ます。

**段階が欠けていたら、その段は落ちています。** 例外にならず静かにルールベースへ
フォールバックするので、`usage.stages` に 5 つ揃っているかが一番早い健全性チェックです。

## 別のモデル・別のプロバイダで試す

`RANK_MODEL` と `SUMMARY_MODEL` にモデル ID を入れると、**モデル ID で自動的に
プロバイダを振り分けます**（`gpt-*` なら OpenAI、それ以外は Anthropic）。
段ごとに混ぜられるので、「採点だけ安いモデル、深掘りは据え置き」も試せます。

### 本番（GitHub Actions）で切り替える

コード変更は不要です。**Settings → Secrets and variables → Actions** で:

| 種類 | Name | Value |
| --- | --- | --- |
| Secret | `OPENAI_API_KEY` | `sk-...` |
| Variable | `RANK_MODEL` | `gpt-5.6-luna` |
| Variable | `SUMMARY_MODEL` | `gpt-5.6-luna` |

Variable を消せば既定（Claude）に戻ります。`ANTHROPIC_API_KEY` は登録したままで
構いません。指定されたモデル ID 側のキーだけが使われます。

### 回す前に 10 秒で確かめる

プロバイダを替えたときの最初の関門は、**構造化出力のスキーマが受理されるか**です。
本番を 10 分回した末に落ちるより先に分かるよう、最小の呼び出しで 4 つのスキーマを試せます。

```bash
OPENAI_API_KEY=sk-... RANK_MODEL=gpt-5.6-luna SUMMARY_MODEL=gpt-5.6-luna npm run check:llm
```

数円で終わります。これが通ってから本番を回してください。

### 同じ入力で A/B を取る

トレンド系のソースは実行のたびに中身が変わるので、そのまま 2 回走らせても
**モデルの差なのか母集団の差なのか分かりません**。収集結果を固定して比べます。

```bash
export SP=/tmp/exp && mkdir -p $SP
export COLLECT_CACHE=$SP/input.json          # 1 回目に作られ、2 回目以降は再利用

ANTHROPIC_API_KEY=... GITHUB_TOKEN=$(gh auth token) \
  npm run collect -- --out $SP/A.json
OPENAI_API_KEY=... GITHUB_TOKEN=$(gh auth token) \
  RANK_MODEL=gpt-5.6-luna SUMMARY_MODEL=gpt-5.6-luna npm run collect -- --out $SP/B.json

npm run compare -- $SP/A.json $SP/B.json
```

`--out` は `data/` を触らないので、実験しても本番データは汚れません。
`compare` は段階別の費用と実行時間、同じ記事に対する判定の一致率
（category / lane / payoff / durability とスコア差）、ベスト N の入れ替わり、
読みどころの文面の見比べを出します。

> 費用を比べるなら**両方とも API キー経由**で実行してください。
> `LLM_BACKEND=claude-code` は従量課金がないので費用が $0 になり、比較になりません
> （`compare` が警告を出します）。

> `SUMMARY_EFFORT` は Anthropic のモデルにしか効きません。`gpt-5.6-luna` で
> `reasoning_effort` が使えるか確認できなかったため、推測でパラメータを送っていません。
> 深掘りの比較は Claude 側がやや有利な条件になります。

## 画面の使い方

- **今日のサマリー** — ページ冒頭に、その日の技術界隈の傾向を3〜5行で書いた
  インサイトが出ます。「セキュリティ関連の修正が多かった」「AI関連の新機能公開が
  続いた」のように、個々の記事の紹介ではなく複数項目を束ねた傾向を LLM が書きます。
  ベスト N・リリース情報・その他の注目記事の要約と、分野・カテゴリ・リリース内訳の
  集計から合成します（生成済みの要約から作るだけなので追加費用はごく僅かです）
- **この先の見立て** — サマリーの最後に一行だけ、いま業界がどの局面にいて、
  この先どこへ向かいそうかを置きます。今日の材料に加えて**直近 7 日分のサマリー**を
  渡し、点ではなく流れとして読ませています。ここだけは推測なので、上の行と
  区切って出し、「〜になりそう」のように推測と分かる語尾で書かせています
- **目次** — ページ冒頭に件数付きのページ内リンクがあります
- **ベスト N のカードは畳んであります。** タップ/クリックで開きます。
  畳んだままでも見出し・元記事タイトル・読みどころ・所要時間が見えるので、
  開く前に読むかどうか決められます
- **読みどころ** — 「何が書いてあるか」（要約）とは別に、
  記事が明らかにした事実を平易な言葉で置いています
- **前提知識はその場で開けます。** 本文中の語に点線と `?` が付いていたら、
  タップ/クリックでその語の説明が出ます。畳んだ「前提知識」一覧からも読めます
- **「◆ 話題」** — はてなブックマークのホットエントリーに載った記事、または
  そのプラットフォームのその日として明確に伸びている記事に付きます。
  他のエンジニアとの共通の話題になりやすい、という目印です
- **潮目 / 手札 / 論点** — 「その他の注目記事」はタブで切り替えます
- **「✳ Claude に聞く」** — その記事の文脈を積んだ状態で Claude の会話を開きます。
  ベスト N・その他の注目記事・リリース情報・検索結果の全部に付いています

## 「✳ Claude に聞く」の仕組み

`https://claude.ai/new?q=<プロンプト>` を開くだけです。API は使わないので**追加費用はゼロ**、
鍵の設定も要りません。ログイン済みの本人のアカウントでそのまま会話が始まります。

- **スマホ** — この URL は Claude アプリの Universal Link / App Link なので、
  アプリが入っていればアプリ側が開きます（入っていなければブラウザ）
- **デスクトップ** — claude.ai のリンクをデスクトップアプリに渡すことはできないため Web 版が開きます。
  そのため押した時点で**同じプロンプトをクリップボードにも入れて**います。
  デスクトップアプリで続けたいときは、アプリを開いて貼ってください
- **渡している中身** — タイトル・URL・出典・サイト側の要約・前提知識・争点・キーワード。
  そのうえで「原文を確認して 300 字で説明し、どこを掘りたいか選択肢にして聞いて」と頼んでいます。
  用途（使い方が分からない／用語が分からない／SNS に書きたい）は毎回違うので、
  ボタンは分けず、掘る方向は Claude 側から聞かせる形にしています
- **URL 長** — 日本語 1 文字が URL エンコードで 9 文字になるため、積めるのは 900 字弱です。
  上限（`web/src/askClaude.ts` の `MAX_ENCODED_LENGTH`）を超える分は、
  優先度の低い節から落とします（要約 → 前提知識 → 争点 → キーワード → 補足 の順に残す）。
  落ちてもクリップボード側には全文が入ります

## 関心トピックを変える

**サイトの「設定」画面から編集できます。** トピック名・重要度(1〜5)・キーワードを、タグ入力の UI で複数追加・削除できます。

設定画面はナビゲーションに出していません。`https://<ユーザー名>.github.io/news-curator/#/settings`
を直接開いてください。読み手向けの画面ではないので導線を絞っているだけで、秘匿ではありません。
開いている間は `noindex, nofollow, noarchive` を立てています（ハッシュはサーバーに送られないため
そもそも別ページとしてインデックスされませんが、明示しています）。

収集処理は GitHub Actions 上で `config/topics.json` を読むので、編集内容は一度リポジトリへ
コミットする必要があります。手順は 3 ステップです。

1. **JSON をコピー** で画面の内容をクリップボードに取る
2. **GitHubで編集** で `config/topics.json` の Web エディタを開く
3. 貼り替えてコミットする（翌朝の実行から反映）

「読者プロフィール」欄も採点精度に直接効きます。使っている技術・立場・何に興味がないかを書くほど精度が上がります。

### 設定画面にアクセストークンは要りません

以前はブラウザに Fine-grained personal access token を貼って GitHub Contents API を
直接叩いていましたが、やめました。公開サイトの localStorage に write 権限付きの
トークンを常駐させる割に、書き込みの認可はリポジトリの権限そのもので足ります。
GitHub の Web エディタへ飛ばせば、ログイン済みで権限があれば編集でき、無ければできない。
リポジトリを private にしてもこの方式のまま動きます。

そのため設定画面には秘密が何もありません。訪問者が編集しても変わるのは
その人自身の localStorage だけです。タブから外しているのは安全のためではなく、
読み手に見せる必要がない画面だからです。

**過去にトークンを保存したことがある場合**、次にサイトを開いた時点で自動的に削除され、
その旨が画面に出ます。ただし削除しても失効はしないので、
[GitHub の設定](https://github.com/settings/personal-access-tokens)から revoke してください。

## 読者フィードバック（Good/Bad）で精度を上げる

ベスト N・その他の注目記事・リリース情報のすべての項目に Good/Bad を付けられます。
直近 14 日ぶんの投票をトピックの重みと LLM への読者コンテキストに反映し、
翌朝以降の採点に効かせます。**ボタンは通常は表示されません。** 認証は追加せず、
URL に秘密のパラメータを渡した本人のブラウザだけで表示を切り替えます。

- スマホでも同じ URL パラメータ方式で動きます（ブラウザは選びません）
- 一度開けば `localStorage` にフラグが残るので、以降は毎回パラメータ不要です
- 投票データは Firestore に保存し、**TTL で 14 日後に自動削除**されます。興味関心が
  変わっても古い投票が残り続けません
- ボタンを押していない大多数の訪問者は、フィードバック機能のコード（Firebase SDK）を
  一切ダウンロードしません（動的 import）

セットアップしなくてもツールは今まで通り動きます。未設定時は完全に無効化されます。

### セットアップ

1. [Firebase Console](https://console.firebase.google.com/) でプロジェクトを作成し、
   Firestore を **Native mode** で有効化する
2. プロジェクト設定 → アプリを追加 → ウェブアプリを登録し、`apiKey` / `projectId` / `appId` を控える
3. Firestore → ルール で以下を貼り付けて公開する

   ```
   rules_version = '2';
   service cloud.firestore {
     match /databases/{database}/documents {
       match /feedback/{articleId} {
         allow read, list, delete: if false;
         allow create, update: if isValidFeedback(articleId);

         function isValidFeedback(articleId) {
           let d = request.resource.data;
           return d.keys().hasOnly([
               'articleId','vote','votedAt','expireAt','digestDate','tier',
               'source','sourceLabel','category','lane','matchedTopics','score','title','url'
             ])
             && d.articleId is string && d.articleId == articleId
             && d.vote in ['good', 'bad']
             && d.votedAt == request.time
             && d.expireAt is timestamp
             && d.expireAt > request.time
             && d.expireAt < request.time + duration.value(15, 'd')
             && d.digestDate is string && d.digestDate.matches('^[0-9]{4}-[0-9]{2}-[0-9]{2}$')
             && d.tier in ['top', 'other', 'release']
             && d.source is string && d.source.size() < 40
             && d.sourceLabel is string && d.sourceLabel.size() < 80
             && d.category is string && d.category.size() < 40
             && (d.lane == null || d.lane in ['know', 'build', 'talk'])
             && d.matchedTopics is list && d.matchedTopics.size() <= 20
             && (d.score == null || (d.score is number && d.score >= 0 && d.score <= 100))
             && d.title is string && d.title.size() <= 300
             && d.url is string && d.url.size() <= 2000 && d.url.matches('^https?://.*');
         }
       }
     }
   }
   ```

   > **レーン導入前から使っている場合は、先にルールを更新してください。**
   > `hasOnly([...])` は許可する項目の**ホワイトリスト**なので、旧ルール
   > （`'domain'` が入っているもの）のままだと、`lane` を送るようになった
   > 新しい画面からの投票がすべて拒否されます。投票の失敗は `console.warn` に
   > 出るだけで画面には出ない（ボタンは押した色に変わる）ため、気づかないまま
   > Good/Bad が 1 件も貯まらない状態になります。
   >
   > 新旧どちらのサイトからの投票も落とさずに移行するには、**両方の項目を許可した
   > ルールを先に公開**してから、サイトをデプロイしてください。旧サイトは `domain`
   > だけ・新サイトは `lane` だけを送るので、**どちらも「無いことがある」前提で
   > 書く必要があります**。`d.domain` のような直接アクセスはキーが存在しないと
   > ルール評価がエラーになって拒否されるため、ここは `get()` を使います。
   >
   > ```
   >   'source','sourceLabel','category','domain','lane','matchedTopics','score','title','url'
   > ...
   >   && (d.get('domain', null) == null || d.get('domain', null) in ['ai', 'general'])
   >   && (d.get('lane', null) == null || d.get('lane', null) in ['know', 'build', 'talk'])
   > ```
   >
   > 新しいサイトからの投票が届いていることを確認したら、`'domain'` を落として
   > 上のルールに揃えます（その時点では `lane` は必ず送られるので直接アクセスで構いません）。
   >
   > なお `rules_version` はルール**言語**のバージョンで、`'2'` のまま変更しません。

   書き込みは投票本人のブラウザから直接行いますが、上のルールで
   `feedback` コレクションへの `create`/`update` 以外（読み取り・一覧・削除）を
   すべて拒否しています。`apiKey` などはこの設計では秘密情報ではありません
   （Firebase のアクセス制御はクライアントの鍵ではなくこのルール側で行います）。
   万一 URL の秘密パラメータが漏れても、実害はスパム投稿程度で、
   しかも 14 日で自動的に消えます。

4. Firestore → TTL で `feedback` コレクションの `expireAt` フィールドに
   TTL ポリシーを設定する（削除の反映まで最大 24 時間ほどかかります）
5. プロジェクト設定 → サービスアカウント → 新しい秘密鍵を生成し、JSON をダウンロードする
   （collector が読み取り専用でサーバー側から集計するために使います）
6. リポジトリの **Settings → Secrets and variables → Actions** に登録する

   | 種類 | Name | Value |
   | --- | --- | --- |
   | Secret | `FIREBASE_SERVICE_ACCOUNT_JSON` | ダウンロードしたサービスアカウント JSON の中身そのまま |
   | Secret | `VITE_FEEDBACK_TOKEN` | 自分だけが知る秘密の文字列 |
   | Variable | `VITE_FIREBASE_PUBLIC_API_KEY` | Firebase の apiKey |
   | Variable | `VITE_FIREBASE_PUBLIC_PROJECT_ID` | Firebase の projectId |
   | Variable | `VITE_FIREBASE_PUBLIC_APP_ID` | Firebase の appId |

   `PUBLIC` が付いている3つは名前の通り秘密にしなくてよい値です。Firebase の
   apiKey はアクセス制御に使われず（アクセス制御は前述の Firestore Security Rules
   が担う）、ビルド済み JS にそのまま入って誰でも見られる前提の値だからです。
   Secrets に入れても動作は変わりませんが、Variables の方が実態と一致します。

7. `https://<ユーザー名>.github.io/news-curator/?fb=<VITE_FEEDBACK_TOKEN の値>` を
   使うブラウザで一度開く。以降そのブラウザでは毎回 Good/Bad ボタンが表示されます

### 反映のされ方

`collector/src/feedback.ts` が直近 14 日ぶんの投票をトピック名（`matchedTopics`）ごとに
集計し、少数の投票で重みが暴れないよう平滑化した上で

- `config/topics.json` の各トピックの重みに 0.75〜1.25 倍の乗数をかけて事前スコアリングに反映
- 変化の大きいトピック上位 3 件を一文にまとめ、LLM の採点・要約プロンプトに追記

します。Firebase を未設定のままにしておけば、この処理は丸ごとスキップされ、
今まで通りの動作になります（LLM バックエンド未設定時にルールベースへフォールバックするのと同じ考え方です）。

### API キーを使わずに生成する（ローカル開発用）

ログイン済みのローカル Claude Code CLI 経由で LLM を呼べます。API キー不要・従量課金なしで、
Claude Code のサブスクリプション枠で動きます（[ai-sdk-provider-claude-code](https://github.com/ben-vargas/ai-sdk-provider-claude-code) を利用）。

```bash
LLM_BACKEND=claude-code GITHUB_TOKEN=$(gh auth token) npm run collect
```

> [!IMPORTANT]
> **ローカル開発・検証専用です。** サブスクリプションの OAuth 認証は Claude Code と
> それをラップする層のためのもので、プロダクトの LLM バックエンドとして常用するのは
> Anthropic のポリシーに反します。CI で `LLM_BACKEND=claude-code` を指定すると
> 明示的にエラーで止まります。本番は必ず `ANTHROPIC_API_KEY` を使ってください。

技術的にも本番向きではありません。実測で比較すると:

| | Anthropic API 直接 | Claude Code CLI 経由 |
| --- | ---: | ---: |
| 入力トークン（採点150件） | 約 54,000 | 291,762 |
| 所要時間（全工程） | 約 30 秒 | 約 7 分 |
| 費用 | 約 $0.19 | $0（サブスク枠） |

エージェントハーネスを経由する分、トークンも時間も大きく増えます。プロンプトを
いじって出力を確かめる用途には十分ですが、毎朝の自動実行には向きません。

**LLM 側に必要なものはありません。** provider が依存する `@anthropic-ai/claude-agent-sdk` が
CLI を同梱していて、認証は macOS キーチェーンに保存済みの Claude Code のログインを使います。
`claude` コマンドが PATH に無くても（mise のシムが壊れていても）動きます。

別のビルドを使いたい場合だけ `CLAUDE_CLI_PATH` で実体を指定できます。

保存せずに結果だけ見る:

```bash
npm run collect:dry
```

過去の日付を指定する:

```bash
npm run collect -- --date=2026-07-30
```

サイトを開く:

```bash
npm run dev
```

http://localhost:5173/news-curator/ が開きます。`data/` と `config/` は dev サーバーが直接配信します。

## チューニング

環境変数（GitHub では **Settings → Secrets and variables → Actions → Variables**）で調整できます。

| 変数 | 既定値 | 説明 |
| --- | --- | --- |
| `RANK_MODEL` | `claude-haiku-4-5` | 採点に使うモデル。安さ優先 |
| `SUMMARY_MODEL` | `claude-sonnet-5` | 深掘りに使うモデル。`claude-opus-5` にすると品質は上がるがコストも上がる |
| `SUMMARY_EFFORT` | `medium` | 深掘りの思考量。`low`〜`max` |
| `TOP_N` | `2` | 深掘りする件数（**レーンごと**なので、2 なら計 6 件） |
| `KNOW_THRESHOLD` | `0.42` | 「知る」に振り分けるしきい値。実行ログの「振り分け」の行を見て調整します |
| `TALK_THRESHOLD` | `0.4` | 「話す」に振り分けるしきい値。同上 |
| `MIN_TOP_SCORE` | `45` | 深掘りするスコア下限。該当が乏しいレーンは件数が減ります |
| `MIN_OTHER_SCORE` | `30` | 一覧に載せるスコア下限 |
| `LANE_CANDIDATES` | `50` | 1 レーンあたりの採点候補数（合計は 3 倍） |
| `OTHER_N` | `12` | 「その他の注目記事」の件数 |

| `BODY_CHAR_LIMIT` | `12000` | 深掘り時に LLM へ渡す本文の最大文字数 |
| `CUTOFF_HOUR` | `7` | 集計の区切り時刻（JST） |

コストを下げたいとき — `SUMMARY_EFFORT` を `low` に、`OTHER_N` を減らす。
品質を上げたいとき — `SUMMARY_MODEL=claude-opus-5`、`SUMMARY_EFFORT=high` に。

`LANE_CANDIDATES` を絞るのは割に合いません。以前 45 まで下げる案を実データで検証したところ、
46〜60 位の帯に実際にベスト入りした記事が含まれていました。削減額は月 ¥80 程度です。

実際にかかった費用は毎回 `data/digests/YYYY-MM-DD.json` の `usage` に工程別で記録され、
サイト末尾にも表示されます。調整の判断はそちらの実測値を見てください。

## 保存されるデータ

| パス | 内容 |
| --- | --- |
| `data/digests/YYYY-MM-DD.json` | その日のダイジェスト全文（ベスト3の深掘り + リリース情報 + その他） |
| `data/index/YYYY-MM.json` | 検索用の月別インデックス（タイトル・要約・キーワード・リンク） |
| `data/manifest.json` | 生成済みの日付・月の一覧と、生成元リポジトリ（設定編集リンク用） |

検索画面はこの月別インデックスを読み込んで、タイトル・要約・キーワード・トピックを対象に AND 検索します。
すべて Git 管理なので、`git log data/` で履歴も追えますし、`grep` でも探せます。

### アーカイブが増えても重くならない仕組み

**読み込みの単位を表示の単位（1 ヶ月）に合わせています。** アーカイブ・検索はどちらも既定で
当月分だけを読み、何年分貯まっても 1 回の転送量は変わりません。

以前は全月をまとめて読んでいました。実測は **14.6KB/日・記事 25 件/日**（gzip で約 1/3.5）なので、
そのままだと 1 年で 5.2MB・13 リクエスト、3 年で 15.6MB・37 リクエストを毎回読むことになります。

検索の「全期間」を選んだときは、**1 リクエスト = 1 ヶ月のまま新しい月から順に**読み込み、
読めた分から結果に反映します。全部揃うのを待たないので、古い月が増えても最初の結果はすぐ出ます。

キャッシュについて。GitHub Pages は `cache-control: max-age=600` 固定で**変更できません**（`_headers` も使えない）。
代わりに、**過去月のインデックスと過去日のダイジェストは書かれた後は変わらない**ので `force-cache` で
転送ゼロで再利用しています。最新分だけ毎回検証します。履歴を作り直したときは
`web/src/api.ts` の `ARCHIVE_CACHE_VERSION` を上げてください（上げないと古いものが残ります）。

### 次の手を打つ目安

現状（1 日あたり index 14.6KB / ダイジェスト 215KB）から見た閾値です。

| 状態 | 到達時期の目安 | すること |
| --- | --- | --- |
| 1 ヶ月分の index が 1MB を超える | 記事数が 2 倍以上に増えたら | 検索用に `summary` を落とした軽量インデックスを別に作る |
| `data/` が 500MB を超える | 約 6 年 | GitHub Pages の 1GB 制限が近い。古いダイジェストを配信対象から外す |

`data/` は年 78MB ずつ増えますが、ダイジェストは**1 日 1 ファイルしか読まない**ので配信は何年でも問題ありません。
index を痩せさせる案は、占有が url 20% / summary 17% / title 15% / keywords 15% と分散していて
**支配的なフィールドが無い**ため、いま実施しても 2 割弱しか減りません（費用対効果が低いので保留）。

## 構成

```
collector/     収集・採点・要約（Node.js + TypeScript、GitHub Actions 上で実行）
web/           閲覧用の SPA（Vite + React、GitHub Pages で配信）
config/        トピック定義・監視対象・ソース定義
data/          生成されたダイジェストと検索インデックス
```

## 注意点

- GitHub Actions の cron は**数分〜十数分遅れることがあります**。収集と要約にも数分かかるため、7:00 ちょうどには更新されません。画面では「毎朝 8:00 までに」と案内しています
- リポジトリを private にすると GitHub Pages の配信に GitHub Pro が必要になります。無料のまま private にしたい場合は、配信先を Cloudflare Pages に変えてください（`BASE_PATH=/` を渡してビルドします）
- Zenn・はてなブックマークの API は非公式のため、仕様変更で壊れる可能性があります。1 つのソースが落ちても、他のソースだけで処理は続行します
